This page is a decision guide. Start by asking whether you need more than one
agent at all, map the work your prompts already do onto a pattern, then grow
into a supervised orchestrator that enforces deadlines, cancellation, and an
approval gate. Each step adds only the coordination the previous one lacked.

## Do you need more than one agent?

Most tasks do not. A single agent with the right tools is simpler to build,
cheaper to run, and easier to debug than any multi-agent setup. Reach for a
second agent only when one of these is true:

- **One prompt is doing too much.** A single system prompt juggling research,
  analysis, and review tends to blur the roles and degrade each one. Splitting
  them into focused agents keeps each prompt sharp.
- **You need isolated context.** A specialist should not see the orchestrator's
  full history, or two sub-tasks should not pollute each other's context window.
- **You want independent iteration.** Different owners, models, or tool sets per
  role, tuned and tested on their own.

If none of these apply, stop here and give one agent more tools. If one does,
the smallest step up is to let that one agent call another agent as a tool.

### Start with the smallest step: an agent as a tool

The simplest multi-agent pattern passes one agent to another as a tool. The
orchestrator reads each specialist's description and calls it when the query
fits, exactly as it would call any other tool. No new orchestration primitive,
just one more tool in the array.

<Tabs>
<Tab label="Python">

```python
from strands import Agent

# A specialized agent, passed directly to an orchestrator's tools
weather_agent = Agent(
    name="weather_agent",
    description="Answers questions about the weather.",
    system_prompt="You are a weather specialist.",
)

# The orchestrator calls the specialist when the query fits
orchestrator = Agent(
    system_prompt=(
        "Route weather questions to weather_agent; answer the rest yourself."
    ),
    tools=[weather_agent],
)

orchestrator("What should I pack for Seattle this weekend?")
```

## Map the work to a pattern

The patterns differ in one thing above all: **how the path of execution is
determined.** The quickest way to choose is to match the pattern to the shape
of work your prompts already describe. Most agent prompts move through some mix
of three phases: **research** (gather), **analysis** (reason), and **review**
(check). Each pattern expresses that shape differently.

| Pattern | How the path is decided | Research → analysis → review shape it fits |
|---|---|---|
| **[Agents as tools](./agents-as-tools.md)** | The orchestrator LLM picks a specialist per query. | One agent delegates a research or analysis sub-question to an expert, then folds the answer back in. |
| **[Workflow](./workflow.md)** | Fixed in code. A task graph (DAG) runs as one reusable tool; independent tasks run in parallel. | A repeatable pipeline packaged behind a single tool call: research, analysis, and review are the same every time. |
| **[Graph](./graph.md)** | Developer-defined edges. Unconditional edges are always followed; a conditional edge is followed only when your predicate, which can inspect model output or app state, returns true. Fixed, parallel, and cyclic flows. | Research feeds analysis feeds review as a fixed chain, or a conditional edge sends the work back to analysis when the review's verdict is a rejection. |
| **[Swarm](./swarm.md)** | Emergent. Agents hand off autonomously through shared context, with no fixed path. | A research, analysis, and review team that reorders itself; review can hand straight back to research. |

### How they compare in depth

Graph and Swarm are SDK orchestrators; Workflow is the `workflow` community tool.
All three share the same foundations: they solve a problem too large for one
agent, they use a single Strands `Agent` as the unit of work, and they pass
information between components toward a final answer. They diverge on control.

| Dimension | Graph | Swarm | Workflow |
|---|---|---|---|
| Core concept | Agents as nodes joined by developer-defined edges; optional conditions route on model output or app state. | A team that autonomously hands off tasks. | A pre-defined task graph (DAG) run as one non-conversational tool. |
| Who defines the path | Developer defines nodes, edges, and edge conditions up front. | Developer provides a pool; agents decide. | Developer defines tasks and dependencies in code. |
| Execution flow | Follows the edges: fixed chains, parallel branches, or conditional routes. | Sequential and autonomous. | Deterministic and parallel. |
| Cycles | Yes. | Yes. | No. |
| State sharing | Shared state object all nodes read and write. | Shared context and working memory. | Task outputs auto-passed to dependents. |
| Error handling | A conditional edge can route on a result a node returns, such as a validator's verdict. Execution errors are not routed to another node. In Python, a node exception raises from the graph call and ends the run. In TypeScript, the failed node records `FAILED`, its downstream nodes do not run, and parallel branches continue. Timeouts end the run in both (see [Graph](./graph.md)). | Agents can hand off to an error specialist; handoff limits and timeouts stop runaway loops by ending the run. | A task whose dependency errored never starts and stays pending. The overall workflow status does not reliably report failure, so check each task's status. |

The sections below give one or two concrete triggers for each.

#### Reach for a Graph

When you want to own the execution path in code: a fixed sequence, parallel
branches, or conditional routes and loops. Unconditional edges run every time;
conditional edges let the next step depend on what the current one returned.

- **Interactive support routing**: branch a conversation on user intent
  ("order question" vs. "address change" vs. "needs a human").
- **Validation with a rejection path**: an agent validates data, and conditional
  edges that read its verdict route the data to a processing node or a
  rejection-handling node. This routes on a returned result. An exception
  raised while a node runs is never routed: in Python it ends the run, and in
  TypeScript the node records `FAILED` and its downstream nodes do not run.

#### Reach for a Swarm

When the problem benefits from several specialized perspectives handing off to
one another. A `Swarm` suits exploration, brainstorming, or synthesizing
sources through collaborative handoffs.

- **Incident response**: a monitoring agent detects an issue and hands off to a
  network specialist, who diagnoses a database problem and hands off to a DBA.
- **Software build**: a researcher hands to an architect, to a coder, to a
  reviewer. The path emerges from the work.

#### Reach for a Workflow

When you have a complex but repeatable process you want an agent to start as
one reusable tool call. If you only need a fixed pipeline in your own code, a
Graph with unconditional edges covers that too.

- **Data pipeline**: a fixed set of extract, analyze, and report tasks, where
  independent analysis steps run in parallel.
- **Standard business process**: onboarding (create accounts, assign training,
  send a welcome email) triggered by a single agent action.

## Grow into a supervised orchestrator

A bare orchestrator does the routing but enforces nothing. Production systems
need guardrails: a node that hangs must be stopped, a cancellation must
propagate instead of leaving work half-done, high-impact steps must pause for a
human, and every handoff must be recorded for audit.

The example below is one supervisor Graph that layers all four onto the
research → analysis → review shape:

1. **Per-node and overall deadlines** so a slow node fails the run instead of
   stalling it.
2. **Cancellation with a recorded reason** so denying a step stops it before it
   runs and records why.
3. **An approval gate** that interrupts before the one high-impact node and
   waits for a human `y/N`.
4. **Handoff logging through a hook** so every node transition is recorded.

<Tabs>
<Tab label="Python">

```python
import json

from strands import Agent
from strands.hooks import BeforeNodeCallEvent, HookProvider, HookRegistry
from strands.multiagent import GraphBuilder, Status


class SupervisorHook(HookProvider):
    """Logs every handoff and gates the one high-impact node for approval."""

    def __init__(self, app_name: str, gated_node: str) -> None:
        self.app_name = app_name
        self.gated_node = gated_node

    def register_hooks(self, registry: HookRegistry) -> None:
        registry.add_callback(BeforeNodeCallEvent, self.on_node)

    def on_node(self, event: BeforeNodeCallEvent) -> None:
        # 4. Record every handoff: BeforeNodeCallEvent fires before each node runs.
        print(f"[handoff] -> {event.node_id}")

        # 3. Approval gate: pause before the one high-impact node and wait
        #    for a human.
        if event.node_id != self.gated_node:
            return

        approval = event.interrupt(
            f"{self.app_name}-approval",
            reason={"node": event.node_id},
        )
        if approval.strip().lower() != "y":
            # 2. Propagate cancellation: deny the node with a recorded reason
            #    instead of letting it run.
            event.cancel_node = f"Human denied the {event.node_id} step"


researcher = Agent(
    name="researcher",
    system_prompt="You gather sources.",
    callback_handler=None,
)
analyst = Agent(
    name="analyst",
    system_prompt="You analyze the research.",
    callback_handler=None,
)
reviewer = Agent(
    name="reviewer",
    system_prompt="You approve or reject the analysis.",
    callback_handler=None,
)

builder = GraphBuilder()
builder.add_node(researcher, "research")
builder.add_node(analyst, "analysis")
builder.add_node(reviewer, "review")
builder.add_edge("research", "analysis")
builder.add_edge("analysis", "review")
builder.set_entry_point("research")

# 1. Per-node and overall deadlines. A node that exceeds its timeout raises
#    from the graph call; the execution timeout is checked before each batch
#    of nodes and ends the run with Status.FAILED.
builder.set_node_timeout(60)        # each node must finish within 60s
builder.set_execution_timeout(300)  # the whole graph within 5 minutes

# Gate the high-impact "review" node behind human approval.
builder.set_hook_providers([SupervisorHook("myapp", gated_node="review")])

graph = builder.build()

# Interrupt/resume loop: the graph pauses at the approval gate and resumes
# only after the human answers.
try:
    result = graph("Research, analyze, and review the Q4 incident")
    while result.status == Status.INTERRUPTED:
        responses = []
        for interrupt in result.interrupts:
            if interrupt.name == "myapp-approval":
                node = interrupt.reason["node"]
                answer = input(f"Approve the {node} step? (y/N): ")
                responses.append({
                    "interruptResponse": {
                        "interruptId": interrupt.id,
                        "response": answer,
                    },
                })
        result = graph(responses)
except RuntimeError as error:
    # 2. A cancelled node raises with its recorded reason and the run ends FAILED.
    print(f"Stopped: {error} (status: {graph.state.status})")
else:
    print(f"Status: {result.status}")
    print(f"Execution order: {[node.node_id for node in result.execution_order]}")
```

### How each guardrail works

- **Deadlines**:
  <Syntax py="builder.set_node_timeout(seconds)" ts="nodeTimeout" />
  bounds any single node and
  <Syntax py="builder.set_execution_timeout(seconds)" ts="timeout" />
  bounds the whole run. A timeout fails the run; it is not routed to another
  node. In Python, a node timeout raises from the graph call, while the
  execution timeout is checked before each batch of nodes and returns a
  `FAILED` result, so it does not stop a node that is already running. In
  TypeScript, either deadline makes `invoke()` throw once the in-flight node
  settles. Timeouts are cooperative: a tool or model call that ignores its
  cancel signal can still run past the deadline.
- **Cancellation with a recorded reason**: setting
  <Syntax py="event.cancel_node" ts="event.cancel" /> to a message skips the
  node and records that message. In Python, the graph call raises a
  `RuntimeError` carrying the message and the run ends `FAILED`. In TypeScript,
  the node and the run end `CANCELLED` and a `NodeCancelEvent` carries the
  message.
- **Approval gate**:
  <Syntax
    py="event.interrupt(name, reason=...)"
    ts="event.interrupt({ name, reason })"
  />
  on `BeforeNodeCallEvent` halts the orchestrator before the gated node. The run
  returns with `Status.INTERRUPTED`; you answer each interrupt by id and resume
  by invoking the graph again. See
  [Interrupts in multi-agent systems](../interrupts-multi-agent.md) for the full
  interrupt/resume contract.
- **Handoff logging**: because `BeforeNodeCallEvent` fires before every node, a
  single callback records each transition. If you prefer to consume handoffs
  from the event stream instead, watch for the `multiagent_handoff` event in
  [`stream_async`](./graph.md#streaming-events).

A [Swarm](./swarm.md) supports the same `BeforeNodeCallEvent` hook and
interrupts, and takes its own node and execution timeouts, so you can apply
this supervision to autonomous handoffs as well.

## Shared state across multi-agent patterns

Both Graph and Swarm support passing shared state to every agent through
<Syntax py="invocation_state" ts="invocationState" />. This shares context and
configuration across agents without exposing it to the LLM. Use it for things
like user ids, feature flags, or a database handle, kept separate from the
data the model should reason about.

<Tabs>
<Tab label="Python">

The `invocation_state` is automatically propagated to:

- All agents in the pattern via their `**kwargs`
- Tools via `ToolContext` when using `@tool(context=True)` (see
  [Custom tools](../tools/custom-tools.md#accessing-state-in-tools))
- Tool-related hooks (BeforeToolCallEvent, AfterToolCallEvent) (see
  [Hooks](../agents/hooks.md#accessing-invocation-state-in-hooks))

```python
import sqlite3

from strands import Agent
from strands.multiagent import GraphBuilder, Swarm

builder = GraphBuilder()
builder.add_node(Agent(name="researcher"), "researcher")
builder.add_node(Agent(name="writer"), "writer")
builder.add_edge("researcher", "writer")
graph = builder.build()

swarm = Swarm([Agent(name="analyst"), Agent(name="reporter")])

# The same invocation_state works for both Graph and Swarm
shared_state = {
    "user_id": "user123",
    "session_id": "sess456",
    "debug_mode": True,
    "database_connection": sqlite3.connect(":memory:"),
}

result = graph("Analyze customer data", invocation_state=shared_state)
result = swarm("Analyze customer data", invocation_state=shared_state)
```

Access it inside a tool:

```python
from strands import ToolContext, tool

@tool(context=True)
def query_data(query: str, tool_context: ToolContext) -> str:
    user_id = tool_context.invocation_state.get("user_id")
    debug_mode = tool_context.invocation_state.get("debug_mode", False)
    # Use context for personalized queries...
    return f"Results for {user_id}"
```

## Where to go next

Start with [Agents as tools](./agents-as-tools.md), the smallest step above a
single agent. Reach for an orchestrator once the order of work matters
or agents must hand off among themselves: [Graph](./graph.md) for
developer-defined edges (fixed, parallel, or conditional), [Swarm](./swarm.md) for
autonomous handoffs, and [Workflow](./workflow.md) for a fixed task graph run
as a reusable tool. To connect agents running as separate services, see
[Agent-to-Agent (A2A)](./agent-to-agent.md). To add supervision (deadlines,
cancellation, and approval gates), see
[Interrupts in multi-agent systems](../interrupts-multi-agent.md).
