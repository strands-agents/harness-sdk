The [Agent-to-Agent (A2A) protocol](https://a2aproject.github.io/A2A/latest/) lets your Strands agents call agents built on other platforms and frameworks, and lets those agents call yours. Strands supports A2A on both sides: consuming a remote agent as a client, and serving one of your own agents over the protocol.

## What is Agent-to-Agent (A2A)?

The Agent-to-Agent protocol is an open standard that defines how AI agents can discover, communicate, and collaborate with each other.

### Use Cases

A2A support covers several patterns:

- **Multi-Agent Workflows**: Chain multiple specialized agents together
- **Agent Marketplaces**: Discover and use agents from different providers
- **Cross-Platform Integration**: Connect Strands agents with other A2A-compatible systems
- **Distributed AI Systems**: Build scalable, distributed agent architectures

Learn more about the A2A protocol:

- [A2A Documentation](https://a2aproject.github.io/A2A/latest/)
- [A2A GitHub Organization](https://github.com/a2aproject/A2A)

:::tip[Complete Examples Available]
Check out the [Native A2A Support samples](https://github.com/strands-agents/samples/tree/main/python/03-integrate/protocols/a2a-native) for complete, ready-to-run client, server and tool implementations.
:::

### Key Concepts

The rest of this page builds on three protocol concepts.

**Agent card.** The JSON document an A2A server publishes at `/.well-known/agent-card.json` to describe its agent: name, description, URL, version, skills, and capabilities. Clients read the card to discover an agent before sending it messages. `A2AAgent` fetches and caches the card for you (see [Fetching the Agent Card](#fetching-the-agent-card)), and the A2A server builds its card from your agent and server options (see [Agent Card](server-configuration.md#agent-card)).

**Context.** A `contextId` identifies one conversation. Messages that share a `contextId` continue the same conversation, and the Strands server keeps separate conversation state for each one (see [Conversation Isolation](#conversation-isolation)).

**Task.** Each request the server handles runs as a task, identified by a `taskId`. A task moves through states such as `working`, `input_required`, `completed`, `failed`, and `canceled`. A task in `input_required` waits until the client answers it with a message on the same task (see [Answering Interrupts](#answering-interrupts)).

## Consuming Remote Agents

You consume a remote A2A agent through the `A2AAgent` class. It wraps the protocol communication behind a familiar interface: you invoke it just like a regular Strands [`Agent`](@api/python/strands.agent.agent#strands.agent.agent.Agent) (Python) / [`Agent`](@api/typescript/Agent) (TypeScript), without resolving agent cards, configuring HTTP clients, building protocol messages, or parsing responses by hand.

### Basic Usage

<Tabs>
<Tab label="Python">

```python
from strands.agent.a2a_agent import A2AAgent

# Create an A2AAgent pointing to a remote A2A server
a2a_agent = A2AAgent(endpoint="http://localhost:9000")

# Invoke it just like a regular Agent
result = a2a_agent("Show me 10 ^ 6")
print(result.message)
# {'role': 'assistant', 'content': [{'text': '10^6 = 1,000,000'}]}
```

### Configuration Options

<Tabs>
<Tab label="Python">

The [`A2AAgent` constructor](@api/python/strands.agent.a2a_agent#strands.agent.a2a_agent.A2AAgent.__init__) accepts these parameters.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `endpoint` | `str` | Required | Base URL of the remote A2A agent |
| `name` | `str` | None | Agent name (auto-populated from agent card if not provided) |
| `description` | `str` | None | Agent description (auto-populated from agent card if not provided) |
| `timeout` | `int` | 300 | Timeout for HTTP operations in seconds |
| `client_config` | `ClientConfig` | None | A2A client config for authenticated transport (SigV4, OAuth, bearer tokens); its `httpx_client` handles both card discovery and message sending |

To reach an authenticated endpoint, pass a `ClientConfig` with a configured `httpx_client`. The `a2a_client_factory` parameter is deprecated; use `client_config` instead.

</Tab>
<Tab label="TypeScript">

The `A2AAgent` constructor accepts a config object with these properties.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `url` | `string` | Required | Base URL of the remote A2A agent |
| `agentCardPath` | `string` | `/.well-known/agent-card.json` | Path to the agent card endpoint |
| `id` | `string` | The `url` value | Unique identifier for the agent instance |
| `name` | `string` | From agent card | Agent name (auto-populated from agent card if not provided) |
| `description` | `string` | From agent card | Agent description (auto-populated from agent card if not provided) |
| `clientFactory` | `ClientFactory` | None | Custom A2A client factory for authenticating requests (SigV4, bearer token) |

The agent card is fetched lazily on the first `invoke()`, `stream()`, or `getAgentCard()` call.

<Tabs>
<Tab label="Python">

import asyncio
from strands.agent.a2a_agent import A2AAgent

async def main():
    a2a_agent = A2AAgent(endpoint="http://localhost:9000")

    async for event in a2a_agent.stream_async("Explain quantum computing"):
        if "data" in event:
            print(event["data"], end="", flush=True)

asyncio.run(main())

## A2AAgent in Multi-Agent Patterns

The `A2AAgent` class integrates with Strands multi-agent patterns that support it. You can use remote A2A agents as nodes in [Graph](../graph.md) workflows and as [tools in an orchestrator agent](#as-a-tool).

### As a Tool

You can wrap an `A2AAgent` as a tool in an orchestrator agent's toolkit:

<Tabs>
<Tab label="Python">

```python
from strands import Agent, tool
from strands.agent.a2a_agent import A2AAgent

calculator_agent = A2AAgent(
    endpoint="http://calculator-service:9000",
    name="calculator"
)

@tool
def calculate(expression: str) -> str:
    """Perform a mathematical calculation."""
    result = calculator_agent(expression)
    return str(result.message["content"][0]["text"])

orchestrator = Agent(
    system_prompt="You are a helpful assistant. Use the calculate tool for math.",
    tools=[calculate]
)
```

## Creating an A2A Server

### Basic Server Setup

Create a Strands agent and expose it as an A2A server:

<Tabs>
<Tab label="Python">

```python
import logging
from strands import Agent
from strands.multiagent.a2a import A2AServer
from strands.vended_tools import notebook

logging.basicConfig(level=logging.INFO)

# Build a fresh agent for each A2A context so callers stay isolated
def create_agent(context_id: str) -> Agent:
    return Agent(
        name="Notebook Agent",
        description="A note-taking agent that organizes information in notebooks.",
        tools=[notebook],
        callback_handler=None
    )

# Create A2A server with a per context agent factory (streaming enabled by default)
a2a_server = A2AServer(agent_factory=create_agent)

# Start the server
a2a_server.serve()
```

</Tab>
<Tab label="TypeScript">

```typescript
import { Agent } from '@strands-agents/sdk'
import { A2AExpressServer } from '@strands-agents/sdk/a2a/express'

```

The server serves the agent card at `/.well-known/agent-card.json` and handles JSON-RPC requests at the root path. Streaming is supported by default.

### Conversation Isolation

The A2A protocol identifies each conversation with a <Syntax py="context_id" ts="contextId" />. The server isolates conversation state per <Syntax py="context_id" ts="contextId" /> so that callers in different contexts never read or influence each other's history. Two modes control how that isolation works.

The recommended mode is an agent factory (<Syntax py="agent_factory" ts="agentFactory" />): you provide a callable that takes a <Syntax py="context_id" ts="contextId" /> and returns a dedicated agent for each conversation, reusing it for later requests in that context. This enables different conversations to run concurrently because each owns an independent agent.

The factory is also where you attach per-conversation state. Both examples below give each conversation its own [session manager](../../agents/session-management.md) keyed on its context ID, so its history persists when the server evicts the context or restarts.

<Tabs>
<Tab label="Python">

```python
from strands import Agent
from strands.multiagent.a2a import A2AServer
from strands.session import FileSessionManager

def create_agent(context_id: str) -> Agent:
    return Agent(
        name="Calculator Agent",
        description="A calculator agent.",
        # One session per A2A context keeps each conversation's history separate
        session_manager=FileSessionManager(session_id=context_id),
        callback_handler=None
    )

a2a_server = A2AServer(agent_factory=create_agent)
a2a_server.serve()
```

</Tab>
<Tab label="TypeScript">

```typescript
import { Agent, SessionManager, FileStorage } from '@strands-agents/sdk'
import { A2AExpressServer } from '@strands-agents/sdk/a2a/express'

--8<-- "user-guide/sdk/multi-agent/agent-to-agent/agent-to-agent.ts:factory_server"
```

</Tab>
</Tabs>

The server retains at most <Syntax py="max_contexts" ts="maxContexts" /> contexts at once (default 1000). When that cap is exceeded, the server evicts the least recently used context, and a later request that reuses the evicted <Syntax py="context_id" ts="contextId" /> gets a newly built agent. Without a session manager, that agent starts a fresh conversation. With one, it restores the saved history. Tune this cap to bound memory in long running servers.

:::caution[The context ID is not an authentication boundary]
Contexts are keyed on the client supplied <Syntax py="context_id" ts="contextId" />. A caller who knows another caller's <Syntax py="context_id" ts="contextId" /> can attach to that conversation. Multi-tenant deployments must enforce authenticated identity at the transport or gateway layer.
:::

:::caution[Passing a single agent is deprecated]
In single-agent mode the server reuses one agent across every context, swapping each context's saved state on and off the shared instance under a lock, which serializes all requests. A single `agent` with a configured <Syntax py="session_manager" ts="sessionManager" /> is rejected, because the session manager would persist every context into one interleaved session. Prefer <Syntax py="agent_factory" ts="agentFactory" /> for any deployment that serves more than one conversation.
:::

### Answering Interrupts

:::note[Python only]
This feature is currently available in the Python SDK only.
:::

When a tool or hook on the served agent raises an [interrupt](../../interrupts.md), the task moves to the A2A `input_required` state and waits for the client to answer. The answer becomes the return value of the [`interrupt()`](@api/python/strands.types.tools#strands.types.tools.ToolContext) call, and the paused tool resumes exactly where it stopped.

This server gives its agent a tool that asks for approval before it launches a campaign:

```python
from strands import Agent, ToolContext, tool
from strands.multiagent.a2a import A2AServer

@tool(context=True)
def launch_campaign(tool_context: ToolContext, name: str) -> str:
    """Launch a marketing campaign once a human approves it."""
    # Pauses the task in input_required until the client answers
    answer = tool_context.interrupt("approve_campaign", reason={"name": name})
    if not answer.get("approved"):
        return f"Campaign {name} was not approved."
    return f"Campaign {name} launched."

def create_agent(context_id: str) -> Agent:
    return Agent(
        name="Campaign Agent",
        description="Launches marketing campaigns after human approval.",
        tools=[launch_campaign],
        callback_handler=None
    )

A2AServer(agent_factory=create_agent).serve()
```

Answering an interrupt needs the raw [`a2a-sdk`](https://github.com/a2aproject/a2a-python) client rather than [`A2AAgent`](@api/python/strands.agent.a2a_agent#strands.agent.a2a_agent.A2AAgent). [`A2AAgent`](@api/python/strands.agent.a2a_agent#strands.agent.a2a_agent.A2AAgent) speaks in text: it raises `ValueError` if you pass it interrupt responses, and it drops the structured data that carries the interrupt ids when it reads the reply.

The server lists the pending interrupts on the `input_required` status message as a `DataPart`, alongside a human-readable `TextPart`. Each interrupt has a server-generated id:

```json
{
  "kind": "data",
  "data": {
    "interrupts": [
      {
        "interruptId": "v1:tool_call:tu-1:a71adb48-e65d-55fa-b155-0359c9cd3b66",
        "name": "approve_campaign",
        "reason": {"name": "spring-launch"}
      }
    ]
  }
}
```

To answer, send a new message with the task's `taskId` and `contextId`, containing one `DataPart` per interrupt that echoes its `interruptId` with your response:

```json
{
  "kind": "data",
  "data": {
    "interruptResponse": {
      "interruptId": "v1:tool_call:tu-1:a71adb48-e65d-55fa-b155-0359c9cd3b66",
      "response": {"approved": true}
    }
  }
}
```

The `response` is any JSON value except `null`. A null answer would leave the interrupt unsatisfied, so the server refuses it. `false` and `0` are fine.

This client sends the request, answers every pending interrupt, and repeats until the task leaves `input_required`:

```python
import asyncio
from uuid import uuid4

from a2a.client import ClientConfig, ClientFactory
from a2a.types import DataPart, Message, Part, Role, Task, TaskState, TextPart

def user_message(parts: list[Part], task: Task | None = None) -> Message:
    # Answers must target the paused task and its context
    return Message(
        message_id=uuid4().hex,
        role=Role.user,
        parts=parts,
        task_id=task.id if task else None,
        context_id=task.context_id if task else None,
    )

async def send(client, message: Message) -> Task:
    async for task, _ in client.send_message(message):
        return task

async def main():
    client = await ClientFactory.connect(
        "http://127.0.0.1:9000", client_config=ClientConfig(streaming=False)
    )
    prompt = Part(root=TextPart(text="Launch the spring-launch campaign."))
    task = await send(client, user_message([prompt]))

    # A resumed tool can interrupt again, so answer until the task moves on
    while task.status.state == TaskState.input_required:
        pending = next(
            part.root.data["interrupts"]
            for part in task.status.message.parts
            if isinstance(part.root, DataPart) and "interrupts" in part.root.data
        )
        answers = [
            Part(root=DataPart(data={
                "interruptResponse": {
                    "interruptId": item["interruptId"],
                    "response": {"approved": True},
                }
            }))
            for item in pending
        ]
        task = await send(client, user_message(answers, task))

    print(task.status.state)
    for artifact in task.artifacts or []:
        for part in artifact.parts:
            if isinstance(part.root, TextPart):
                print(part.root.text)

asyncio.run(main())

# Typical output:
# TaskState.completed
# The spring-launch campaign has been launched.
```

The server validates an answer before the agent runs and rejects one it cannot bind with a JSON-RPC invalid-params error. The interrupt stays pending, so the task is still answerable. An answer is rejected when:

- its `interruptId` does not match an interrupt the task is waiting on
- no interrupt is pending
- the same `interruptId` is answered twice in one message
- the payload is missing `interruptId`, or its `response` is missing or `null`
- it is sent alongside other content parts

A task with a pending interrupt also rejects an ordinary conversational message. Answer the interrupt, or cancel the task.

A `DataPart` without an `interruptResponse` key is unaffected and continues to reach the agent as structured data.
