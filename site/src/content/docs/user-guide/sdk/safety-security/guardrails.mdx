Guardrails control what an agent accepts, what it does, and what it returns. A guardrail
on the model screens prompts and model responses. It does not see tool arguments, the
identity of the caller, or the content that a tool retrieves. An agent that calls tools
needs a check at each of those points. This page shows how to build those checks with
tool input schemas, [interventions](../agents/interventions/index.mdx), and Amazon
Bedrock Guardrails, and how to combine them on one agent.

The examples use the TypeScript SDK. The intervention actions that they return
(`proceed`, `deny`, `guide`, `confirm`, and `transform`) are also available in the
Python SDK.

Each layer handles one kind of failure:

| Layer | Catches | Runs |
|-------|---------|------|
| Schema | Malformed tool input | When the tool is called |
| Rules | Tool calls that break a rule you can express in code | Before a tool call |
| Classifier | Abuse, prompt injection, and off-topic requests | Before a model call |
| Confirmation | High-impact tool calls | Before a tool call |
| Tenant policy | Tool calls the tenant's policy does not permit | Before a tool call |
| Retrieval boundary | Retrieved text that reads as instructions | After a tool call |

Handlers that implement the same lifecycle method run in registration order, and a
`deny` skips the remaining handlers for that method. Register inexpensive rules before
handlers that pause for approval or call a service. The classifier implements
`beforeModelCall`, which runs before the model requests a tool, so its position
relative to the `beforeToolCall` handlers has no effect.

## Validate tool input with a schema

Define the constraints on a tool's input in its input schema. When a tool call fails
validation, the SDK returns the parse error to the model as an error tool result, and
the tool callback does not run. A schema checks only the shape of the input. For file
paths, also resolve each path in the tool callback and verify that it is inside the
allowed directory:

The model receives the schema in the tool specification, so the schema also guides the
model toward valid tool calls. Do not use a prefix check on the path string as the
boundary. A path such as `/tmp/agent-scratch/../etc` passes a prefix check, and a
symbolic link inside the directory can point outside it. `realpath` resolves both
before the comparison.

`deny` to block the tool call, or `guide` to cancel it and tell the model what to
change:

Set `onError` to `'deny'` on a handler that enforces a rule. If the handler throws an
error, the SDK then blocks the tool call. With the default value, `'throw'`, the error
ends the invocation. Intervention handlers run before the SDK validates tool input
against the schema, so check the type of each field before you use it.

## Screen content with a classifier

Use a classifier for content that rules cannot describe, such as abuse, prompt
injection, and off-topic requests. The classifier can be Amazon Bedrock Guardrails,
another moderation service, or a model that you host.

The following handler screens the most recent user message before each model call. The
classifier is a network call, so the handler sets a time limit and defines what happens
when the classifier does not respond within it:

In `shadow` mode, the handler logs each verdict and does not block the request. Use
this mode to measure the false positive rate on production traffic, and then change
`mode` to `enforce`. Choose the `onTimeout` value for your application. An internal
tool can allow the request and rely on the other layers. A public agent in a regulated
domain should block it.

When the guardrail blocks user input, the SDK redacts that input from the conversation
by default, so that the next turn is not blocked by the same text. For the redaction
options, see [Amazon Bedrock](../model-providers/amazon-bedrock.mdx#guardrails).

Use both. The intervention handler provides the time limit, the timeout behavior, and
shadow mode. The model guardrail can block a model response. An intervention handler
cannot, because `afterModelCall` supports `guide` and `transform` but not `deny`.

## Confirm high-impact tool calls

To require approval for tool calls that are large or cannot be undone, return `confirm`
from a handler. The agent stops before the tool runs, and the invocation returns with
the `interrupt` stop reason. Show the prompt to an approver, and then invoke the agent
again with the response:

The handler decides from the tool input, so a tool call that deletes five files or
fewer runs without a pause. Intervention handlers run before schema validation, so the
handler first checks that `paths` is an array and returns `guide` if it is not. Without
that check, a malformed tool call causes an error in the handler, and with the default
`onError` value that error ends the invocation.

In a stateless deployment, the approval arrives in a different process. Use a
[session manager](../agents/session-management.mdx) to persist the interrupted state
between requests. For allow lists, a risk classifier, or approval that applies for the
rest of a session, use the
[`HumanInTheLoop`](../agents/interventions/human-in-the-loop.mdx) handler.

## Apply per-tenant policies with an audit record

To give each tenant its own tool permissions, store a [Cedar](https://cedarpolicy.com)
policy for each tenant and load it when you create the agent. Give each policy a
version, so that you can change a tenant's permissions without deploying code:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:tenant_policy_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy_type"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy"
```
</Tab>
</Tabs>

Cedar denies by default. A tool call that no `permit` statement matches is blocked, so
a tenant whose policy does not permit `delete_files` cannot delete files. The principal
comes from `invocationState`, which your application sets from the authenticated
request. If the resolver returns `undefined`, the handler denies every tool call. For
policy schema validation and hot reload, see
[Cedar authorization](../agents/interventions/cedar-authorization.mdx).

To record each decision, wrap the handler that makes it and log the action that the
handler returns. The record then includes the name of the handler. Do not derive the
record from `event.cancel` in a hook that runs later. That property does not identify
the handler that denied the tool call, and it is not set while a confirmation is
waiting for a response:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:audit_record_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy_type"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:audit_record"
```
</Tab>
</Tabs>

When you wrap the Cedar handler, the wrapper records `allowed` or `denied` with the
policy version. When you wrap a handler that returns `confirm`, the wrapper raises the
interrupt. It records `pending` when the agent stops, and `approved` or `denied` after
the invocation resumes. The SDK runs the `beforeToolCall` handlers again on resume, so
the log contains a Cedar record both before and after the approval.

A record describes a decision. It does not show that the tool ran, because a later
handler can deny a tool call that Cedar allowed. To record the outcome of a tool call,
log `event.result.status` from `afterToolCall`. Write audit records to append-only
storage.

## Keep retrieved text from escalating permissions

Search results, web pages, and files can contain text that is written to look like
instructions, and the model might follow it. Two of the preceding layers limit the
effect. The principal and the role come from `invocationState`, which the model cannot
read or change. Cedar evaluates every tool call against that principal, including tool
calls that the model makes after it reads retrieved text.

As an additional layer, mark retrieved text as untrusted before the model reads it:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:retrieval_boundary_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:retrieval_boundary"
```
</Tab>
</Tabs>

The handler escapes the text and the attribute value. Without escaping, retrieved text
that contains `</retrieved>` closes the block, and the text after it appears to come
from your application.

The markup is a defense-in-depth measure. It tells the model how to treat the text but
does not prevent the model from following it, so authorization and confirmation remain
the controls that block a tool call. Do not let a tool result set `invocationState`,
add text to the system prompt, or register a tool. For message history that comes from
a source you do not control, see
[Trusted message history](./trusted-message-history.mdx).
