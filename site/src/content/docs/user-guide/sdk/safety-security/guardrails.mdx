A guardrail on the model boundary screens prompts and responses. It does not see
tool arguments, the caller's identity, or text a tool retrieved, so an agent that acts
needs more than one. This page layers checks on an agent, each placed where it catches
one kind of failure cheaply, using [interventions](../agents/interventions/index.mdx),
[hooks](../agents/hooks.mdx), and a model-provider guardrail.

The examples are TypeScript and use the intervention actions `proceed`, `deny`,
`guide`, `confirm`, and `transform`. The same actions exist in the Python SDK. Each
code block carries its own imports and definitions, so you can copy one on its own.

| Layer | Catches | Runs on |
|-------|---------|---------|
| Schema | Malformed tool input | Tool definition |
| Rules | Calls that break a rule you can code | Before tool call |
| Classifier | Abuse, injection, off-topic requests | Before model call |
| Confirmation | High-impact calls | Before tool call |
| Tenant policy | Calls the tenant or role is not allowed | Before tool call |
| Retrieval boundary | Retrieved text used as instructions | After tool call |

Ordering applies within one lifecycle stage. Handlers that implement `beforeToolCall`
run in registration order, and a `deny` from one skips the rest of them, so register
the cheap deterministic checks before the ones that pause or cost money. The
classifier runs on `beforeModelCall`, before the model has proposed any tool call, so
the tool-call rules neither precede it nor short-circuit it. It is the one network call
in the stack, so it gets a time budget and a fallback.

## Validate tool input with a schema

Put every constraint you can express as a type in the tool's input schema. The parse
error returns to the model as an error tool result, and the model corrects the call
before your code runs. Then canonicalize anything the tool touches on disk, in the
tool, immediately before acting:

The schema is the one layer the model reads directly, in the tool specification, so it
steers the model toward valid calls as well as rejecting invalid ones. It validates
shape, not location. A prefix check on the string passes `/tmp/agent-scratch/../etc`,
and a symlink inside the directory points wherever it likes, so the string is never the
filesystem boundary. The resolved path is, and only the tool can resolve it.

## Enforce deterministic rules

violations and `guide` when the model can fix the call itself:

Set `onError` to `'deny'` on any handler that enforces a rule. A thrown error then
blocks the call instead of letting it through. Rules are plain code with no model
involved, which makes them the one layer you can unit test exhaustively.

## Screen content with a classifier

Abuse, prompt injection, and off-topic requests cannot be enumerated as rules. Hand the
text to a classifier instead: Amazon Bedrock Guardrails, OpenAI's moderation endpoint,
or a model you host. Wrap it behind one interface so the handler does not care which.

A classifier is a network call on every turn, so give it a budget and decide now what
happens when it misses. The handler screens the latest user message before each model
call, aborts the classifier at the budget, and applies the fallback you configured:

Start in shadow mode. It logs every verdict without enforcing one, which gives you the
false-positive rate on real traffic before anyone is blocked. Switch to enforce once
the log looks right. The fallback is a product decision: an internal tool can allow on
timeout and rely on the layers below, while a public agent in a regulated domain blocks
on timeout and shows a retry message.

## Confirm high-impact tool calls

To route large or irreversible actions past a person without slowing routine ones,
return `confirm` from a handler. The agent pauses before the tool runs and resumes with
the answer. Above the threshold the invocation stops with the `interrupt` stop reason.
Show the prompt to an approver, then resume with their answer:


The line is drawn on the input, not the tool. Interventions see that input before the
schema does, so a handler that indexes into it without narrowing throws on a malformed
call, and under the default `onError` of `'throw'` that error surfaces instead of the
schema's correctable one. Check the shape first and return an action.

In a stateless deployment the approval arrives on another process, so pair this with a
[session manager](../agents/session-management.mdx) to persist the paused state. For
per-tool allow lists, a model-based risk classifier, or a remembered "trust this tool"
answer, use the vended [human in the loop](../agents/interventions/human-in-the-loop.mdx)
handler instead of writing your own.

## Apply per-tenant policies with an audit record

To run one codebase under many contracts, keep each tenant's rules in a
[Cedar](https://cedarpolicy.com) policy loaded by version. A change to one tenant's
rules is a policy edit and a version bump, not a deploy:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:tenant_policy_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy_type"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy"
```
</Tab>
</Tabs>

Cedar is default-deny: a tool with no matching `permit` is blocked, so a tenant whose
policy omits `delete_files` cannot delete anything. The principal comes from
`invocationState`, which only your server populates from the authenticated request.
With no identity the resolver returns `undefined` and every tool call is denied. Policy
schema validation and hot reloading are on the
[Cedar authorization](../agents/interventions/cedar-authorization.mdx) page.

Record each decision where it is made. A hook that runs after the intervention pipeline
and reads `event.cancel` cannot do this: an earlier rule may have denied the call
before Cedar ran, and a pending confirmation raises an interrupt without setting
`cancel`, so the hook would log a denial against the wrong layer or an approval that
does not exist yet. Wrap the handler instead and log the action it returns:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:audit_record_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:tenant_policy_type"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:audit_record"
```
</Tab>
</Tabs>

Each record names its source. Wrapped around the Cedar handler it logs `allowed` and
`denied` with the policy version that produced them. Wrapped around a confirmation
handler it logs `pending` when the call stops for a person and `approved` or `denied`
when the answer comes back, because the answer passes through the action's `evaluate`
function on resume. Resuming runs the `beforeToolCall` stage again, so a Cedar record
appears on both sides of the approval.

These are decisions, not executions. A Cedar `allowed` can still be denied by a later
handler or wait on an approver. If you need a record that the tool ran, log it from
`afterToolCall`, where `event.result.status` says how the call ended. Write the records
somewhere append-only. The question you will be asked is "which policy version allowed
this call, and who was the principal", and this is the record that answers it.

## Keep retrieved text from escalating permissions

A search result, a fetched page, or a file an agent reads can contain text written to
look like an instruction. The model reads it as one. Your stack must not.

Two properties above already do most of the work. Identity and role come from
`invocationState`, which the model never sees and cannot write. And Cedar checks every
tool call against that identity, so an instruction inside a tool result meets the same
policy the user does. Add a third: mark retrieved text as untrusted before the model
reads it:

<Tabs>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/safety-security/guardrails_imports.ts:retrieval_boundary_imports"

--8<-- "user-guide/sdk/safety-security/guardrails.ts:retrieval_boundary"
```
</Tab>
</Tabs>

Escape the text and the attribute. Retrieved content that contains its own closing tag
would otherwise end the untrusted block early and leave whatever follows it looking
like your text. The block is framing, not enforcement: it tells the model how to read
what follows, and a model can be talked out of that. Authorization and confirmation
remain the boundary. Never let a tool result set `invocationState`, append to the
system prompt, or register a tool. Each of those turns retrieved text into an
instruction with authority. For history you load from a source you do not control, see
[trusted message history](./trusted-message-history.mdx).
