The SDK estimates how much of the model's context window is in use so it can trigger compression before overflow. Three pieces work together: the context window limit, token counting, and utilization estimation.

## Context window limit

The threshold check requires the model's context window size. The SDK auto-populates <Syntax py="context_window_limit" ts="contextWindowLimit" /> from built-in lookup tables for known models. The SDK matches the base model ID, and strips region and provider prefixes such as `global.` and `openai.` before the lookup.

**The lookup tables are best effort.** They can lag a provider release, and they do not cover private or fine-tuned models. Set <Syntax py="context_window_limit" ts="contextWindowLimit" /> explicitly for any production workload. An explicit value always takes precedence over the tables, and it pins the behavior across SDK upgrades.

<Tabs>
<Tab label="Python">

Set it explicitly, or override the [lookup table](https://github.com/strands-agents/harness-sdk/blob/main/strands-py/src/strands/models/_defaults.py):

```python
model = BedrockModel(
    model_id="my-custom-model",
    context_window_limit=128_000,
)
```
</Tab>
<Tab label="TypeScript">

Set it explicitly, or override the [lookup table](https://github.com/strands-agents/harness-sdk/blob/main/strands-ts/src/models/defaults.ts):

:::caution[Inaccurate compression with default fallback]
The SDK can use a default limit of 200,000 tokens. This occurs when <Syntax py="context_window_limit" ts="contextWindowLimit" /> is not set and the SDK cannot match the model ID to the lookup table. The SDK then emits a warning that names the model ID.

A wrong limit makes every utilization figure wrong. Compression can then start far earlier than you expect, on a fraction of the real context window. Repeated compression changes the start of the prompt, which also prevents prompt-cache reuse and raises cost. Set the limit explicitly to prevent this.
:::

## Token estimation

The agent estimates input tokens using the following strategy:

1. **Known baseline**: reads <Syntax py="input_tokens + output_tokens" ts="inputTokens + outputTokens" /> from the last assistant message's usage metadata
2. **Delta estimation**: estimates tokens for new messages added since that baseline using the model's <Syntax py="count_tokens()" ts="countTokens()" /> method
3. **Cold start fallback**: when no prior usage metadata exists (first call or after session restore), estimates all messages via <Syntax py="count_tokens()" ts="countTokens()" />

The <Syntax py="count_tokens()" ts="countTokens()" /> method uses a character-based heuristic by default (characters / 4 for text, characters / 2 for JSON). Some model providers support native token counting APIs for exact counts. For an example in both SDKs, see [Amazon Bedrock token counting](../model-providers/amazon-bedrock/#token-counting).

## Utilization estimation

The Model base class provides an <Syntax py="estimate_utilization(input_tokens)" ts="estimateUtilization(inputTokens)" /> method that computes the fraction of the context window consumed by a given input token count:

<Tabs>
<Tab label="Python">

```python
ratio = model.estimate_utilization(
    input_tokens=projected_tokens,
)
# ratio is 0-1+ (above 1.0 means overflow)
```
</Tab>
<Tab label="TypeScript">

```typescript
--8<-- "user-guide/sdk/context-management/context-estimation_imports.ts:utilization_imports"

--8<-- "user-guide/sdk/context-management/context-estimation.ts:utilization"
```
</Tab>
</Tabs>

The method divides <Syntax py="input_tokens" ts="inputTokens" /> by the model's <Syntax py="context_window_limit" ts="contextWindowLimit" />, falling back to the 200,000 default with a warning when not configured. A return value above 1.0 means overflow.

Both the built-in [context management modes](./built-in-modes) and the [conversation managers](../agents/conversation-management) use this internally for compression decisions. You can also call it directly when building custom logic.
