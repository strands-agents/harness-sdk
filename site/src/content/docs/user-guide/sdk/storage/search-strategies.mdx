Storage backends expose a
<Syntax py="search()" ts="search()" /> method that
delegates to a pluggable search strategy. A strategy
implements the
<Syntax py="SearchStrategy" ts="SearchStrategy" />
protocol/interface: given a storage backend and a query
string, it returns a ranked list of matching keys with
relevance scores. Strategies that maintain an index use
<Syntax py="index()" ts="index()" /> to update
incrementally on each write;
<Syntax
  plain
  py="strategies that search on the fly implement it as a no-op"
  ts="strategies that search on the fly omit it"
/>.

All shipped backends default to
`KeywordSearchStrategy`. Pass a different strategy via
the
<Syntax
  py="search_strategy"
  ts="searchStrategy"
/> parameter on any built-in backend to override it.

## KeywordSearchStrategy

The default strategy shipped with both SDKs. Tokenizes
the query into lowercased words, reads every key in
storage, and scores each entry by the number of distinct
query tokens that appear in the key and content. No
index, embedding model, or external dependency required.

Because it reads every entry on each search, keyword
search is best suited for small-to-medium stores (up to
a few thousand keys). For larger stores, use the BM25
strategy.

## BM25 search

BM25 full-text search backed by a SQLite inverted
index. Scores results by term frequency, inverse
document frequency, and document length normalization,
producing significantly better relevance ranking than
keyword overlap for large stores. It works only with
`LocalFileStorage`, because it keeps its index file on
the host filesystem next to the storage directory. For
the same reason it can't be used with a sandboxed
`LocalFileStorage`; use keyword search there, which
works with every backend.

<Tabs>
<Tab label="Python">

`Bm25SearchStrategy` uses the built-in `sqlite3` FTS5
module, with no external dependencies. It indexes
entries at write time and never re-scans storage, so
only content written after the strategy is attached is
searchable (there is no backfill).

## S3 Vectors search

Semantic (vector) search for `S3Storage`, backed by
[Amazon S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html).
`S3VectorSearchStrategy` embeds each value on write and
stores the vector in an S3 Vectors index, removes it on
delete, and embeds the query on search to find the
nearest stored entries. The vectors are a derived index
over the bucket: every write costs one embedding call
plus a `PutVectors` request.

<Tabs>
<Tab label="Python">

Not yet available in the Python SDK.

</Tab>
<Tab label="TypeScript">

It works only with `S3Storage`; attaching it to another
backend is a type error. By default it uses the vector
bucket `<bucket>-vectors`, the index `default`, a
`BedrockEmbedder` (Amazon Titan Text Embeddings V2),
and the storage's region:

```typescript

--8<-- "user-guide/sdk/storage/search-strategies.ts:s3_vector_search"
```

The vector bucket and index are not created for you.
Create them before the first write, with a dimension
that matches the embedder (1024 for Titan Text
Embeddings V2):

```bash
aws s3vectors create-vector-bucket --vector-bucket-name my-bucket-vectors
aws s3vectors create-index --vector-bucket-name my-bucket-vectors \
  --index-name default --data-type float32 --dimension 1024 --distance-metric cosine
```

#### Required IAM permissions

At runtime, the IAM user or role needs the following
permissions on the vector index, on top of the S3
permissions `S3Storage` already needs:

- `s3vectors:PutVectors` (on write)
- `s3vectors:DeleteVectors` (on delete, and on writes
  of empty or non-UTF-8 values)
- `s3vectors:QueryVectors` (on search)
- `bedrock:InvokeModel` on the embedding model (with the
  default `BedrockEmbedder`)

Here's a sample IAM policy for the default setup:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3vectors:PutVectors",
                "s3vectors:DeleteVectors",
                "s3vectors:QueryVectors"
            ],
            "Resource": "arn:aws:s3vectors:*:*:bucket/my-bucket-vectors/index/default"
        },
        {
            "Effect": "Allow",
            "Action": "bedrock:InvokeModel",
            "Resource": "arn:aws:bedrock:*::foundation-model/amazon.titan-embed-text-v2:0"
        }
    ]
}
```

Creating the vector bucket and index needs
`s3vectors:CreateVectorBucket` and
`s3vectors:CreateIndex`, but only for setup; the
strategy never creates resources itself.

Keep these in mind:

- Only content written after the strategy is attached
  is searchable; there is no backfill.
- Empty and non-UTF-8 values are stored but not
  indexed, and remove any earlier vector for that key.
- Vectors are keyed by the full object key, so storages
  on one bucket under different prefixes (including
  `namespace()` views) can share an index. Don't share
  one index across different buckets.
- Query and stored vectors must come from the same
  model. If you change the embedder, use a new index.

To use another model or provider, pass your own
`embedder`. An embedder extends the `Embedder` abstract
class and implements
`embed(text, { purpose })`, where `purpose` is
`'document'` when indexing and `'query'` when
searching:

## Passing a strategy to a storage backend

Every built-in backend (`InMemoryStorage`,
`LocalFileStorage`, `S3Storage`) accepts a
<Syntax
  py="search_strategy"
  ts="searchStrategy"
/> parameter. When set, writes automatically call the
strategy's
<Syntax py="index()" ts="index()" /> method, and
<Syntax py="search()" ts="search()" /> delegates to
the strategy instead of the default keyword scan.

## Writing a custom strategy

To rank results your own way, implement
<Syntax py="SearchStrategy" ts="SearchStrategy" />
yourself. Its <Syntax py="search()" ts="search()" />
method receives the storage backend and the query, and
returns
<Syntax py="StorageSearchResult" ts="StorageSearchResult" />
entries (key, score, and optionally the stored bytes),
best match first. Read entries through the storage
passed in, using
<Syntax py="list()" ts="list()" /> and
<Syntax py="read()" ts="read()" />, so the strategy
works with every backend. When the search already read
an entry's bytes, include them in the result as `data`
so callers don't have to read the entry again.

If your strategy keeps its own index, such as a vector
store or a full-text index, update it in
<Syntax py="index()" ts="index()" />. The backend calls
it on every write with the key and the stored bytes.

The example below ranks entries by how often the exact
query phrase appears.

<Tab label="Python">

`SearchStrategy` is a protocol, so any class with async
`index()` and `search()` methods works without
subclassing. `index()` is required; a strategy that
searches on the fly implements it as a no-op.

To pass a strategy to a sandboxed `LocalFileStorage`,
declare `requires_host_fs: Literal[False] = False` on
the class, as `KeywordSearchStrategy` does. The type
checker rejects a sandboxed `LocalFileStorage` with a
strategy that doesn't declare it. If your strategy
reads or writes the host filesystem directly, declare
`requires_host_fs: Literal[True] = True` instead, as
`Bm25SearchStrategy` does, and `LocalFileStorage`
raises `ValueError` when a sandbox is set.

</Tab>
<Tab label="TypeScript">

Any object or class with a `search()` method works.
`index()` is optional; a strategy that searches on the
fly omits it.
