:::note[New to Strands?]
Start with **[Strands harness](../harness/)** for a fully assembled, state-of-the-art agent harness. It's built on the Strands Harness SDK with opinionated, benchmarked defaults for the system prompt, tools, memory, sessions, and context management, and every default is overridable.

Use the **Strands Harness SDK** when you want to build an agent harness from the ground up, piece by piece.
:::

An agent harness is the software around a model that turns it into an agent. The Strands Harness SDK is for building one yourself, end to end.

It runs the loop and gives you the pieces you attach to it: tools, memory, sessions, plugins, and interventions. The same code takes you from prototype to production.

## A running agent

The smallest agent is a model with the loop around it. Create one and invoke it:

<Tabs>
<Tab label="Python">


## Strands harness or the Strands Harness SDK?

Strands gives you two starting points, and you can move between them without a rewrite.

| If you want to... | Start with | Why |
|---|---|---|
| Get a complete agent harness with tested defaults | [Strands harness](../harness/) | The decisions are already made: system prompt, tools, memory, sessions, context management, and a production loop come pre-wired and benchmarked. You start from a working agent. |
| Build the agent harness yourself, piece by piece | [Strands Harness SDK quickstart](./quickstart/python/) | Nothing is pre-decided. You get the primitives and the loop, and you choose every component and how they fit. |
| Start on Strands harness and drop down for more control later | [Compose with the Strands Harness SDK](../harness/composing-with-sdk/) | Strands harness is built on the Strands Harness SDK, so any piece is yours to swap out without a rewrite. |

Weighing Strands against other frameworks or a hand-written loop instead? See [choosing an agent foundation](../migrate/choosing-an-agent-foundation/).

## Frequently asked questions

These five questions cover choices that often come up when building an agent.

<Tabs>
<Tab label="Models">

**Can I keep my current model when I move to Strands?**

You can keep the model when its provider supports the capabilities your agent
needs. The agent loop is separate from the
[model provider](./model-providers/), so you can change providers without
restructuring the agent. You still need to adapt tools, state handling, and
multi-agent behavior to the Strands APIs.

</Tab>
<Tab label="Languages">

**Should I use Python or TypeScript?**

Use the SDK that matches your application's runtime. Both support the core agent
loop, tools, streaming, structured output, sessions, and the main multi-agent
patterns. Support for features and providers varies; bidirectional agents are
currently Python-only. Start with the [Python quickstart](./quickstart/python/) or
[TypeScript quickstart](./quickstart/typescript/).

</Tab>
<Tab label="Tools">

**Should I build a custom tool or use an MCP tool?**

Use a [custom tool](./tools/custom-tools/) for application code registered
directly with an agent. Use an [MCP tool](./tools/mcp-tools/) when the tool is
discovered and called through an MCP server. An agent can use both types
together.

</Tab>
<Tab label="Multi-agent">

**Which multi-agent pattern fits my application?**

Choose based on who should control the execution path. Agents as tools keep a
coordinator in control; A2A connects deployed services; graphs define allowed
paths; swarms let agents choose handoffs; workflows put fixed dependencies in
code. [Compare the patterns](./multi-agent/multi-agent-patterns/).

</Tab>
<Tab label="State">

**How do sessions, memory, and context management work together?**

[Sessions](./agents/session-management/) restore conversation and agent state.
[Memory](./memory/overview/) carries selected knowledge across sessions.
[Context management](./context-management) controls what stays in the active
model window. Applications often use all three.

</Tab>
</Tabs>
