Use background tasks when a tool takes time and the agent has other work it can do.
The tool runs in the background, the agent receives a task ID, and its loop continues.
When the result is ready, the SDK adds it to the conversation so the agent can use it.

Background tasks are disabled by default in the SDK. Enable them with the
<Syntax py="background_tasks" ts="backgroundTasks" /> option on `Agent`.
[Strands harness](../../harness/configure/background-tasks.md) enables them by default
and always runs its `subagent` tool in the background.

## Run a tool in the background

This example simulates a slow report query. It always runs `build_report` in the
background and keeps other tools in the foreground. Configure a
[model provider](../model-providers/) before running it; these examples use the default
Amazon Bedrock provider.

<Tabs>
  <Tab label="Python">
    ```python
    import asyncio

    from strands import Agent, tool


    @tool
    async def build_report(region: str) -> str:
        """Build an example sales report for a region."""
        await asyncio.sleep(1)
        return f"Example report for {region}: revenue grew 12%."


    async def main() -> None:
        agent = Agent(
            tools=[build_report],
            background_tasks={
                "always": [build_report],
                "never": ["*"],
                "max_concurrency": 2,
                "timeout": 30,
            },
        )
        result = await agent.invoke_async(
            "Build the north region report. While it runs, outline three "
            "questions to ask about sales growth. Then summarize the report."
        )
        print(result)


    asyncio.run(main())
    ```

The model still decides whether to call a tool. An `always` policy controls how a
tool call executes; it does not cause the call itself.

By default, the invocation waits for outstanding background work before returning,
so the final response can include the report.

### What happens during the call

<Diagram
  name="background-task-delivery"
  alt="Background task dispatch and delivery, as a sequence between the model, the agent, and a background task. Dispatch: the model requests a tool call, the agent queues the tool as a background task, and returns a receipt with the task ID to the model. Continue: the agent makes its next model call while the tool runs in the background. Delivery: the task reports that its result is ready, and the agent delivers the result to the model before the next model call."
/>

1. **Dispatch.** The model requests a tool call and the SDK applies the tool's execution
   policy. A background call is queued, and the model receives a receipt with the task
   ID, tool name, and status instead of the tool's result.
2. **Continue.** The agent loop moves on. The tool starts when a background execution
   slot is free.
3. **Delivery.** Before a later model call, or when the invocation would otherwise
   finish, the SDK adds ready results to the conversation and the agent continues.

[Tool executors](executors.md) order the foreground tool calls in one model response.
Background tasks use a separate queue, so the loop continues before those calls finish.
Direct calls through `agent.tool` always execute in the foreground, even for a tool
with an `always` policy.

## Choose an execution policy

Set <Syntax py="background_tasks=True" ts="backgroundTasks: true" /> to let the model
choose background execution for all compatible tools. Pass a configuration object
when you need finer control.

Each policy accepts tool instances, registered tool names, or the wildcard `"*"`:

| Policy | Behavior when the model calls a matching tool |
| --- | --- |
| `agentic` | The model chooses foreground or background execution. |
| `always` | The tool runs in the background. |
| `never` | The tool runs in the foreground. |

Exact matches take precedence over a wildcard. For example, `always` containing
`build_report` plus `never` containing `"*"` backgrounds only the report tool.
Putting the same selector in two policies is an error.

If you omit `agentic`, it defaults to `["*"]`, unless `always` or `never` contains
`"*"`. If you provide `agentic`, only its selectors apply, and tools that no policy
matches stay in the foreground. An empty `agentic` list therefore turns off
model-selected background execution.

### Tools eligible for model-selected execution

For an `agentic` tool, the SDK adds an optional `_background_execution` boolean to
the schema shown to the model, and removes it from the input before calling your tool.
Don't declare a parameter with that name on your own tools.

Adding the flag requires an object input schema without a top-level `$ref`, `allOf`,
`anyOf`, `oneOf`, `not`, `if`, `then`, or `else`. Naming an incompatible tool in
`agentic` is an error; a wildcard match leaves it in the foreground.

Some tools always stay in the foreground: the background-task management tool,
structured-output tools, context-management tools, and agents configured with
<Syntax py="delegate=True" ts="delegate: true" />. Don't name them in `agentic` or
`always`. The SDK rejects that configuration, or returns an error result for the call.

## Configure limits and options

`BackgroundTasksConfig` describes the configuration object. Every option is optional;
the defaults apply when you pass <Syntax py="True" ts="true" /> or an empty object.

| Option | Default | Meaning |
| --- | --- | --- |
| `agentic` | `["*"]` | Tools whose execution mode the model chooses. |
| `always` | `[]` | Tools that run in the background. |
| `never` | `[]` | Tools that run in the foreground. |
| <Syntax py="wait_for_completion" ts="waitForCompletion" /> | on | Wait for background work before returning. |
| <Syntax py="max_concurrency" ts="maxConcurrency" /> | `4` | Tasks that may execute at once. A positive integer. |
| `timeout` | none | Limit for one execution: seconds in Python, milliseconds in TypeScript. |
| <Syntax py="manage_tool_name" ts="manageToolName" /> | See below | Name of the [management tool](#receive-and-inspect-results). |

Tasks beyond the concurrency limit wait in submission order. The timeout starts when
execution starts, so time spent queued does not count. A timed-out task becomes
`failed` with a `timeout` error. Python accepts any positive number of seconds;
TypeScript requires a whole number of milliseconds no larger than `2_147_483_647`.

These limits apply to one agent's background work. Tools still share the host
process and its resources. Use asynchronous I/O for waiting operations; CPU-bound
JavaScript still blocks the event loop.

## Receive and inspect results

When you enable background tasks, the SDK registers a management tool named
`strands_manage_background_task`. The model can call it to list, inspect, or cancel
tasks, and doesn't need to poll: the SDK delivers results automatically.

A delivered result appears in the conversation as a call to the management tool with
`mode: "get"`, followed by its result. The first content block holds the task
metadata; the tool's own output follows in its original content blocks, images
included. Once delivered, the task leaves the management tool's list. The result
stays in conversation history, subject to normal context management.

To give the management tool another name, set
<Syntax py="manage_tool_name" ts="manageToolName" />. The name must not match another
tool on the agent. It's written into conversation history, so keep it stable for the
life of a saved session.

### Task states

| Status | Meaning |
| --- | --- |
| `queued` | Waiting for an execution slot. |
| `working` | The tool is executing. |
| `input_required` | Execution paused for an interrupt response. |
| `completed` | The tool finished successfully. |
| `failed` | The tool returned an error, raised an exception, or timed out. |
| `cancelled` | Cancellation was requested and recorded. |

The last three states are terminal. A task stays listed in a terminal state until its
result is delivered.

Task metadata includes <Syntax py="task_id" ts="taskId" />,
<Syntax py="tool_use_id" ts="toolUseId" />, <Syntax py="tool_name" ts="toolName" />,
`status`, and creation and update timestamps. The task ID identifies the background
work and differs from the original tool-use ID.

Failed tasks include an `error` with a `type` and `message`. The type is
<Syntax py="tool_error" ts="toolError" /> for an error the tool returned,
<Syntax py="execution_error" ts="executionError" /> for an exception during execution,
and `timeout` for an expired timeout. Check the task's `status` and `error` rather than
the tool result's status: a successful `get` can describe a failed task.

## Return while tasks are still running

Set <Syntax py="wait_for_completion" ts="waitForCompletion" /> to
<Syntax py="False" ts="false" /> for detached execution. The invocation then returns
when the agent finishes its turn, even with work outstanding. Results that are ready
before then are still delivered during the invocation.

The SDK does not invoke an idle agent when a detached task finishes. Your application
invokes the same agent again, either with a new user request or with
<Syntax py="await agent.invoke_async([])" ts="await agent.invoke([])" />.
An empty invocation adds no user message. It delivers any ready results, then calls
the model, whether or not a result was ready. Wait for the previous invocation to
finish before starting another.

Keep the process alive while tasks run. In an asynchronous Python application, also
keep the event loop the tool started on: closing that loop cancels the task.

With the default wait setting, the SDK delivers completed tasks between model calls.
If the agent finishes its turn with tasks outstanding, the invocation waits for all of
them, delivers the results, and continues.

### List, inspect, and cancel from your application

Call the management tool directly to work with tasks from application code. It has
three modes:

| Mode | Request | Response content |
| --- | --- | --- |
| `list` | No task ID. | A `tasks` array of task IDs, tool names, and statuses. |
| `get` | A task ID. | Task metadata followed by available tool output. |
| `cancel` | A task ID. | The task ID and resulting status. |

Use the ID from the dispatch receipt or from `list`. Inspecting a task with `get`
does not consume its automatic delivery. After delivery the task is gone, and `get`
or `cancel` for its ID returns an error result.

This example starts a slow tool, inspects the tracked tasks, and cancels unfinished
work. Direct management calls do not invoke the model. Setting
<Syntax py="record_direct_tool_call=False" ts="recordDirectToolCall: false" />
also keeps those calls out of the conversation.

<Tabs>
  <Tab label="Python">
    ```python
    import asyncio

    from strands import Agent, tool


    @tool
    async def build_report(region: str) -> str:
        """Build an example report after a simulated slow query."""
        await asyncio.sleep(10)
        return f"Example report for {region}: revenue grew 12%."


    async def main() -> None:
        agent = Agent(
            tools=[build_report],
            system_prompt="Report cancelled tasks without retrying them.",
            background_tasks={
                "always": [build_report],
                "never": ["*"],
                "wait_for_completion": False,
            },
        )
        await agent.invoke_async(
            "Start the north region report and tell me it has started."
        )

        manage = agent.tool.strands_manage_background_task
        listing = manage(mode="list", record_direct_tool_call=False)
        tasks = listing["content"][0]["json"]["tasks"]
        for task in tasks:
            print(manage(
                mode="get",
                task_id=task["task_id"],
                record_direct_tool_call=False,
            ))
            if task["status"] in {"queued", "working", "input_required"}:
                manage(
                    mode="cancel",
                    task_id=task["task_id"],
                    record_direct_tool_call=False,
                )

        # Deliver any recorded outcomes to the agent.
        print(await agent.invoke_async([]))


    asyncio.run(main())
    ```

## Cancel background work

Cancelling a task records the `cancelled` outcome and signals the tool to stop.
Cancellation is cooperative: it does not guarantee that an external operation or a
blocking function has stopped. Have your tools check
<Syntax py="tool_context.cancel_signal" ts="context.cancelSignal" /> and pass it to
libraries that support cancellation. In Python the signal is a `threading.Event`;
in TypeScript it is an `AbortSignal`.

Cancel one task with the management tool's `cancel` mode. To cancel every queued,
working, and input-required task at once, call
<Syntax
  py="agent.cancel(cancel_background_tasks=True)"
  ts="agent.cancel({ cancelBackgroundTasks: true })"
/>.
On an idle agent, that call cancels only the tasks and leaves the next invocation alone.

A plain `agent.cancel()` stops the current invocation and leaves background tasks
running. If the invocation had already finished its turn and was only waiting for
background tasks, it returns that turn's result, and the outstanding results are
delivered on the next invocation. For the rest of the cancellation contract, see
[cancellation](../agents/agent-loop.md#cancellation).

## Handle interrupts

A background tool can request input through
<Syntax py="tool_context.interrupt()" ts="context.interrupt()" />.
Execution middleware can also request an interrupt. The task enters
`input_required` and releases its execution slot, so other background tasks continue.

The agent surfaces the request through the normal
[interrupt and resume flow](../interrupts.md). Supply a response for each interrupt,
then invoke the agent with those responses. The task is queued again and the tool
runs from the beginning with a fresh timeout, with the earlier responses available.
Place irreversible side effects after the approval, or make them safe to repeat.

A before-tool hook runs in the foreground before the task is submitted, so it can
still request approval for the call itself.

Interrupts raised inside a child agent don't reach the parent when the child runs in
the background. This applies to agents wrapped with
<Syntax py="Agent.as_tool()" ts="Agent.asTool()" /> and to the
[`subagent`](vended-tools/subagent.md) tool: the task fails with an
<Syntax py="execution_error" ts="executionError" /> naming the interrupt. Keep an agent
tool in the foreground if its child needs approval.

## Observe execution

Background tools run through tool execution [middleware](../agents/middleware.md) and
the tool lifecycle [hooks](../agents/hooks.md). The before-tool hook runs at dispatch.
The after-tool hook runs when the tool finishes and receives its actual result, not
the dispatch receipt.

Progress events that a background tool streams are not part of the invocation's event
stream. In Python they go to the agent's
[callback handler](../streaming/callback-handlers.md); in TypeScript they fire
`ToolStreamUpdateEvent` hooks. Account for overlapping work when those callbacks
update shared application state.

The management tool reports task status and finished results. It has no mode for
progress updates or for sending a message to a running task.

## Persist state and recover after a restart

Background task metadata and undelivered results are part of agent state. A
[session manager](../agents/session-management.md) or
[snapshot](../agents/snapshots.md) saves that state through the normal persistence
lifecycle. A task update does not by itself trigger a durable write.

Restoring state keeps saved terminal outcomes for delivery and marks saved
unfinished tasks as failed. It does not resume the running function or restart an
external job. For work that must survive a process restart, have your tool submit the
work to a durable service and return that service's job ID.

Loading a snapshot into an agent that still tracks background tasks is rejected,
including when every task is terminal but undelivered. Finish or cancel the work and
deliver its outcomes before loading another snapshot.
