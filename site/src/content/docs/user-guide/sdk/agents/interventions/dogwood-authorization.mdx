Dogwood Authorization evaluates a [Dogwood](https://github.com/dogwood-policy/dogwood)
policy set before each tool call. Dogwood is Cedar with temporal conditions, so a policy
can decide based on what the agent already did in this session, not only on the call in
front of it. Approve a refund after a fraud check ran. Allow a delete once the record was
read.

For access control that depends only on the current call, use
[Cedar Authorization](./cedar-authorization.mdx) instead: the same policy language
without the temporal conditions, and without Dogwood's extra dependency.

## How it works

The handler spans both halves of a tool call. Before the call it submits a `request` event
and enforces the verdict. After the call it records a `response` event, or an `error`
event if the tool threw, which is what later temporal rules match against.

| Dogwood concept | Maps to | Example |
|---|---|---|
| **Principal** | User identity | `User::"alice"` |
| **Action** | Tool name | `Action::"search"` |
| **Resource** | The agent itself | `Resource::"agent"` |
| **context.input** | Tool arguments | `{ query: "quarterly report" }` |
| **Event history** | Calls and results so far | `formerly within 1h …::response{}` |

A generated schema declares its actions and entities at the top level, so policies name
`Action::"search"` and the default principal is `User::"anonymous"`. Pass a `namespace` to
declare them under your own domain instead, which every rule then qualifies as
`Acme::Action::"search"`. A hand-written <Syntax py="action_schema" ts="actionSchema" />
declares its own namespace, so the option is only valid with `tools`.

Policies are default deny: a tool with no matching `permit` is blocked, and the agent
receives the denial reason as feedback.

Passing `tools` generates the Cedar action schema from your tool specs, and the
constructor type-checks the policy set against it. A misspelled tool name, in a `permit`
or inside a temporal predicate, throws immediately rather than leaving the rule silently
unenforced. Pass <Syntax py="action_schema" ts="actionSchema" /> instead when you maintain
the schema yourself.

Generated action ids are the tool names verbatim, so every tool name must be a legal Cedar
identifier. A name containing `-`, `.`, or a space fails schema generation and throws.

A hand-written schema must declare the entity types the handler actually sends: `Resource`
for the resource, which is always `Resource::"agent"` under whatever namespace the schema
declares, and `User` for the default principal. A policy that names an entity type the
schema does not declare fails validation in the constructor.

A condition compares the tool arguments as the model emitted them, and a generated schema
is typed to match: write `context.input.method == "DELETE"` for an enum parameter, whose
constraint is dropped so the value stays a plain string. A misspelled value is just
another string, so it fails to match rather than failing to compile. Reading a parameter
the tool does not mark required needs a `has` guard,
`context has input.retries && context.input.retries == 3`, or the constructor throws.

Number parameters are typed for what each SDK's Dogwood binding accepts, so a comparison
on one is written differently in each.

In Python, a `float` parameter is a Cedar `decimal`, which has no `<` or `>`: write
`context.input.amount.lessThan(decimal("10.0"))`. A whole number the model sends is
widened to match, so `{"amount": 2}` compares equal to `decimal("2.0")`, and an argument
carrying more than the four decimal places Cedar holds is denied before any policy runs.
An `int` parameter is a `Long` and takes the ordering operators directly.

In TypeScript, a `z.number()` parameter is declared as a whole number, so
`context.input.retries > 3` works, and comparing a fractional argument with `<`, `>`,
`<=`, or `>=` is an evaluation error that denies the call. Equality is unaffected: `== 3`
simply does not match `3.5`. See the
[Dogwood language reference](https://github.com/dogwood-policy/dogwood) for the full type
rules.

Match on `response` events for rules that mean "this already happened and finished", and
on `error` events for "this failed". Dogwood records an event into history before deciding
it, so a rule written against `request` events also matches the call being decided and
satisfies itself on the first call.

A rule that unlocks one tool with another's `response` needs the calls ordered. The
default concurrent tool executor decides every call in a turn before recording any
result, so the rule above does not fire when the model emits both calls at once. Set the
agent's <Syntax py="tool_executor" ts="toolExecutor" /> to the
[sequential executor](../../tools/executors.mdx), as the example does, and each call is
decided after the previous one has been recorded.

Each recorded event carries the action, the principal, and the tool's arguments, so a
temporal predicate can key on an argument, as in `response{ input.query: "audit" }`. It
does **not** carry the tool's return value: a predicate on a result field, such as
`response{ output.hits: 0 }`, type-checks cleanly against a tool that declares an
`outputSchema` and then never matches, so the rule looks enforced and silently is not.
The same holds for the `requestId` and `sessionId` fields the default event schema
declares. Write `response{}` or `error{}`, optionally narrowed by `input.*`.

Dogwood itself supports result-keyed rules; this handler not recording `output` is the
limitation, because a tool result is arbitrary content rather than a value shaped like
the declared `outputSchema`.

An `error` event is recorded when the tool failed, and nothing at all is recorded for a
call a later handler blocked, because that tool never ran. In TypeScript, a tool that
catches its own failure and returns an error result — including an MCP tool returning
`isError: true` — also leaves no event, because the executor reports a blocked call the
same way.

When <Syntax py="principal_resolver" ts="principalResolver" /> returns
<Syntax py="None" ts="undefined" />, the handler denies the call. No identity, no access.

Correlating history by principal needs nothing beyond the resolver. Every temporal
predicate is pinned to the principal being decided, so one handler instance serves many
users without their histories mixing: a search alice ran never unlocks a delete for bob.

A generated schema declares `User` as its only principal type, qualified by `namespace`,
so a resolver returning any other type denies the call and a static `principal` of another
type throws at construction. An undeclared type is not an error to Dogwood: a rule that
scopes the principal simply never matches, so a `forbid` would silently not apply.

A policy that needs a field the tool arguments do not carry reads it from the `session`
context group, which <Syntax py="context_enricher" ts="contextEnricher" /> fills from
<Syntax py="invocation_state" ts="invocationState" />: the policy reads it as
`context.session.<field>`. Those fields reach the `when { … }` condition only, because the
event schema declares a tool's arguments and nothing else, so a temporal predicate cannot
reference an enriched field.

:::note[Enriched fields need a declared schema in Python]
Dogwood checks a request's context against the action's declared context type, and a
generated schema cannot declare the enricher's group. Python's `context_enricher`
therefore requires an `action_schema` that declares a `session` group on every tool
action, and the constructor raises when it does not. TypeScript's `contextEnricher` is
accepted against a generated schema.
:::

Files are read, parsed, and validated in the constructor. There is no re-read at runtime,
so an edited policy file takes effect the next time the handler is constructed.

## History and memory

History is never pruned; it grows with every call the handler decides, at roughly 1.7 KB
per event in TypeScript's wasm module. `reset()` drops it and keeps the handler deciding:


Calling `reset()` means holding the handler in a variable, as the example does, rather
than constructing it inline in the `interventions` array: an agent exposes no way to
reach an intervention back once it is built.

`reset()` clears every principal the instance has decided for, not one user's history.
A multi-tenant handler that resets when one session ends discards everyone else's, and
interventions are fixed at construction, so isolating histories means one agent per
session rather than one handler per session.

History lives in memory only. It does not survive a process restart, and it is not part
of an agent's session state, so a resumed conversation starts with an empty history and a
rule waiting on an earlier call will not fire.

## When a decision fails closed

Dogwood forces a deny on any evaluation error and clears the determining rules, so an
error means something went wrong rather than the policy saying no. The handler reports the
two cases with different denial reasons.

Tool arguments come from the model, so a request event can be malformed by a prompt. A
decision that throws is treated as no decision and denies, naming the mismatch so the
model can act on it when it retries. In Python the schema is enforced before any policy
runs, so an argument the tool does not declare — or a required one the model left out —
denies the call rather than reaching the tool.

A binding that can no longer be trusted to decide fails closed for good. In TypeScript a
wasm trap denies that call and every call after it. In Python a panic in the native
binding ends the run rather than returning a verdict, and the handler denies every call
after it.

The <Syntax py="on_error" ts="onError" /> option controls what happens when the handler
itself throws, for example when
<Syntax py="principal_resolver" ts="principalResolver" /> raises:

- `'throw'` (default): rethrows to the caller
- `'deny'`: treats the failure as a denial
- `'proceed'`: runs the tool with no authorization check

:::caution[Fail-open on handler errors]
With `'proceed'`, an exception from your resolver or enricher lets the tool call run
unchecked. Use `'deny'` when the agent relies on Dogwood to enforce access. A failed
Dogwood decision denies regardless of this setting.
:::

## Installation

Dogwood evaluation runs through an optional dependency:

<Tabs>
<Tab label="Python">

```bash
pip install strands-agents[dogwood]
```

The handler imports `dogwood` at module load, so importing
`strands.vended_interventions.dogwood` raises an `ImportError` naming the extra when the
package is missing.
</Tab>
<Tab label="TypeScript">

```bash
npm install @strands-agents/sdk @aws/dogwood-wasm
```

The handler imports `@aws/dogwood-wasm` at module load, so the import throws when the
package is missing. The module is about 9.4 MB on disk (2.9 MB gzipped).
</Tab>
</Tabs>

[Dogwood](https://github.com/dogwood-policy/dogwood)'s authors describe the
implementation as a reference interpreter rather than a production one, and the published
bindings inherit that, so treat this handler as experimental.
