You give the optimizer an experiment and a goal. It makes new versions of your agent, tests them on the cases of the experiment, and recommends the best version as a set of edits.
You decide which edits go into the agent. The optimizer is `strands-evals optimize run` of [Strands Evals](/docs/user-guide/evals-sdk/), and `/optimize` asks for its settings one question at a time.
For the proposers, the model that ranks the candidates, and the files of a run, see [Inside the optimizer](/docs/user-guide/cli/dev/optimizer-internals/).

## What the optimizer can change

The optimizer changes the options of the `createHarness` or `create_harness` call. The options are the knobs of the run:

- The instructions or the system prompt, the model, and the effort.
- Prompt caching, the context manager, and background tasks.
- Each skill, tool, built-in tool, MCP server, plugin, built-in plugin, and intervention, on or off.

An option that the call leaves out starts from the default of the harness. When you apply its edit, dev writes the option into the call.
A knob that dev cannot change shows the reason. Session and memory are not knobs, because each trial runs without them.

For the Base CLI, the optimizer can tune only the options that a profile can hold. See [Improve the Base CLI](/docs/user-guide/cli/dev/base-cli/#optimize-the-base-cli).

## How the cases divide

The optimizer divides the cases of the experiment into three parts:

- **Train** cases guide the search for new versions.
- **Validation** cases pick the winner.
- **Test** cases measure the winner on cases that the search did not see.

By default, half of the cases are train cases, and the other half divides equally into validation and test cases. With fewer than 2 validation cases or 2 test cases, the scores can be luck. Then the review tells you how many cases to add.

## How the search goes

The search has steps. In each step, the optimizer makes new versions of the agent, the candidates, and runs each candidate on the train cases.
A proposer model writes the new text for a text knob, such as the instructions. Each run of the agent on one case is a rollout.

To average out noise, a case can run more than one time for each candidate. A run with 0 steps makes no candidates. It only measures the current agent.

## How a version gets its score

The goal of the run is the objective:

- By default, the optimizer increases the mean score of all the evaluators of the experiment.
- It can decrease a usage metric instead: tokens, output tokens, seconds, or model calls.
- It can balance several metrics, with a weight for each metric or as a set of best trade-offs.

Constraints are limits that the winner must also meet, for example "tokens at most 4000" or "OutputEvaluator at least 0.8". Each limit applies to the average of one run of one case.
On the validation cases, a candidate must meet each constraint with 90% certainty by default. By default, a run that crashes gets the worst score of each evaluator.

## How the optimizer picks the version that it recommends

The best candidates of the search are the finalists, 3 by default. The optimizer runs them again on the validation cases, and the finalist with the best average score wins.
For a cautious pick, the optimizer compares a low estimate of each score instead, at 75% or 90% certainty.

Then the winner and the current agent run on the test cases. The report gives the score before and after. The edits of the winner are the recommendation.

## What a run costs

The review in the chat shows the estimated rollouts and judge calls before the run starts.
The default budget is 4 steps with 4 candidates in each step, 1 run of each case, and 3 finalists. 4 trials run at the same time.
One run can use at most 500 rollouts. Above that, the review asks for fewer steps, candidates, or runs. Each rollout and each judge call is a paid model call.

## Why you approve each edit

A small experiment can make a lucky candidate look best. Thus dev shows the recommendation as a diff, one edit at a time, and you apply or leave each edit. The agent changes only with the edits that you apply.
To apply the edits without a review, turn on **Auto-accept optimization results**. See [Optimize automatically](/docs/user-guide/cli/dev/auto-optimize/).

## Recommendations

- For a first run, use a small budget, for example 2 steps.
- Give the experiment enough cases for at least 2 validation cases and 2 test cases.
- When the goal is only fewer tokens or less time, add a quality constraint, for example "OutputEvaluator at least 0.8". Without one, an agent that answers badly, or not at all, can look best.
- After you apply edits, run the experiment again from `/experiment` to measure the change.
- Commit the agent file and the experiment file together.
