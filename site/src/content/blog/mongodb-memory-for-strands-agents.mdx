The longer you work with an agent, the less you should have to repeat.

Decisions and lessons from previous tasks should carry forward. Work in progress
should survive a restart. Persisting conversation history helps with the
restart. Finding relevant knowledge from an earlier task requires searchable
long-term memory.

The MongoDB team built `strands-mongodb`, a Python integration that adds
persistent sessions and searchable long-term memory to Strands Agents.

## Why two backends?

Suppose an agent learns that a project's integration tests use a separate
database. If the process restarts, the agent should return to the same
conversation. When a new conversation turns to test setup, the agent should
still recall the database requirement.

Strands handles those jobs through separate interfaces:

| Job | MongoDB backend | How the agent uses it |
| --- | --- | --- |
| Resume a conversation | `MongoDBStorage`, used by `SnapshotSessionManager` | Loads saved session state using a session ID. |
| Recall knowledge across conversations | `MongoDBMemoryStore`, used by `MemoryManager` | Searches stored facts within a scope, such as a project or user. |

Use either backend on its own, or point both at the same MongoDB deployment.

## Getting started

The [MongoDB integration guide](/docs/integrations/integrations/mongodb/) covers
installation, Atlas setup, credentials, and a cross-session recall test.
Complete that setup, then save this example as `mongodb_memory.py`:

```python
"""Persist Strands sessions and long-term memory in MongoDB."""

import asyncio
import os

from strands import Agent
from strands.memory import MemoryManager
from strands.models import BedrockModel
from strands.session import SnapshotSessionManager
from strands_mongodb import MongoDBMemoryStore, MongoDBStorage


MEMORY_SCOPE = "project-123"
DEFAULT_PROMPT = (
    "Remember: this project uses pytest, and integration tests "
    "use a separate database."
)


async def main():
    session_id = os.getenv("SESSION_ID", "conversation-001")
    prompt = os.getenv("PROMPT", DEFAULT_PROMPT)

    # Session state and long-term memory share this deployment.
    config = {
        "connection_string": os.environ["MONGODB_URI"],
        "database": "agents",
        "search_type": "vector",
    }

    storage = MongoDBStorage(config, collection="sessions")
    memories = MongoDBMemoryStore(
        name="project_notes",
        config=config,
        scope=MEMORY_SCOPE,  # Keep stable to share facts across conversations.
        writable=True,
        extraction=True,  # Extract facts into long-term memory.
    )

    try:
        async with Agent(
            model=BedrockModel(
                model_id="us.anthropic.claude-haiku-4-5-20251001-v1:0",
                region_name="us-east-1",
            ),
            storage=storage,
            session_manager=SnapshotSessionManager(
                session_id=session_id,  # Reuse to resume; change to start fresh.
                save_latest_on="message",  # Save after every message.
            ),
            # Adds memory search and injects relevant memories into context.
            memory_manager=MemoryManager(stores=[memories]),
        ) as agent:
            response = await agent.invoke_async(prompt)
            print(response)

        # Leaving the context flushes pending memory extraction.
    finally:
        await memories.close()
        await storage.close()


if __name__ == "__main__":
    asyncio.run(main())
```

Run the example once with its default values. It saves the conversation as
`conversation-001` and stores the project's test requirements under
`project-123`.

To test long-term recall, start a new session while keeping the same memory
scope, then ask what test setup the project requires. The new conversation never
receives the original message, but the answer should still mention the separate
database. The integration guide includes the command.

## Search and memory controls

Vector search retrieves memories by meaning, while full-text search matches
specific terms. On supported deployments, hybrid search combines both. A
compatible Atlas deployment can generate embeddings for stored memories and
queries, so the agent does not need separate embedding code.

Memory scopes limit retrieval to a user or project, while authorization remains
the application's responsibility. Repeated writes of identical content are
deduplicated within a store and scope. Set `ttl_seconds` when memories should
expire.

The snippet selects vector search explicitly. Automatic mode can fall back to
text search, so check the active mode before testing semantic recall.
