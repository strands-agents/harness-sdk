# Shared

What the SDKs and the harness must agree on: data, constants and lists that exist in Python and TypeScript alike. Anything in this folder has a copy or loader in each SDK and a parity test that fails when a copy drifts.

## `model-info.json`

What the SDKs know about models: context windows, output ceilings, which models take cache points, which models Strands forces to call the structured output tool, which have native structured output, which accept temporary messages, which take tools on the OpenAI Chat Completions API, which cannot call tools on their provider, and the id rules that map a provider's model id to the entry that describes it. Each entry is a `ModelInfo`, the same type the SDK exposes, plus the few fields that type does not carry (`capabilities.defaultEffort` for the harness, `capabilities.chatCompletionsTools` for the OpenAI Chat Completions provider, and `capabilities.toolUse`, which no consumer reads yet); every field is optional and a missing field means unknown.

Edit the file; each SDK copies it into its own package when it installs and builds, and does not commit the copy:

- `strands-ts`: the `prepare` (any `npm ci` / `npm install`) and `prebuild` scripts `cp` it to `strands-ts/src/models/model-info.json` (git-ignored). Run `npm run prepare -w strands-ts` after editing to refresh it. `model-info.test.node.ts` asserts the copy equals this file.
- `strands-py`: the `hatch_build.py` build hook copies it to `strands-py/src/strands/models/model_info.json` (git-ignored). `test__model_info.py` asserts the copy equals this file.
- `harness-ts`: `prepare` / `prebuild` copy it to `harness-ts/src/model-info.json` (git-ignored); `test/model-info.test.ts` asserts the copy equals this file.
- `harness-py`: `hatch_build.py` copies it to `harness-py/src/strands_harness/model_info.json` (git-ignored); `tests/test__model_info.py` asserts the copy equals this file.

Each consumer reads only the fields it uses and skips the rest, so a field one consumer needs (the harness's `capabilities.defaultEffort`) needs no change in the others.

### Format

Keys and multi-word values are camelCase, matching the TypeScript `ModelInfo` type (`cachePoints`); the Python loader re-cases both on read (`cache_points`). There is no version field: the shape is the SDK's `ModelInfo` type, each SDK's tests validate every entry strictly against it and those few extra fields, and a shape change updates the loaders in the same PR. `capabilities.stateful` is owned by the provider and is not read from this file. `capabilities.temporaryMessages` says which models accept temporary messages and use their text; only a provider that can send them acts on it. Claude Haiku 5.5 accepts them but rarely uses the text, so it is `false`. `capabilities.forcedToolChoice` is also `false` for Claude Haiku 5.5, although the model accepts a forced tool choice: a forced call skips thinking, so its structured output uses native output instead. That makes the entry a choice, not a fact about the model; #6236 has the measurements and what would let it go back to `true`. `capabilities.chatCompletionsTools` records a model OpenAI's Chat Completions API limits tools for: `reasoningOff` when it accepts them only with `reasoning_effort: "none"`, `unsupported` when it accepts none. It is not part of `ModelInfo`; the SDKs' OpenAI Chat Completions provider reads it, and acts on it only for `api.openai.com` and Bedrock Mantle, where it was measured. `capabilities.toolUse` is `false` for a model measured as unable to call tools on Bedrock (Converse, ConverseStream, InvokeModel), and is left out otherwise. Only `mistral.magistral-small-2509` has it: Bedrock accepts the tools but returns the model's tool call as text (`[TOOL_CALLS]echo{"value": "pineapple"}`), so no tool runs and structured output through a tool fails; [#6241](https://github.com/strands-agents/harness-sdk/issues/6241#issuecomment-6969381418) has the measurements. It is not part of `ModelInfo` and the SDKs do not act on it. TODO: measure again and remove it once Bedrock returns the call as a tool use.

- `defaults`: what the SDK assumes when a model's entry does not say, today `limits.contextWindow`. Defaults are the SDK's policy, not a fact about any model, so they live apart from `models`.
- `models`: one entry per model, keyed by the shortest id that names it (`claude-opus-5-5`, `gpt-5.4`, `amazon.nova-pro-v1:0`). A lookup tries the id as given, then without a trailing Bedrock version suffix (`-v1:0`), then without a trailing date (`-20260401`, `@20251001`), then with leading dot-separated segments removed one at a time. So `us.anthropic.claude-opus-5-5-20260401-v1:0`, an ARN and `claude-opus-5-5` all resolve to the one `claude-opus-5-5` entry. Add a separate entry only when the same model differs between providers (`openai.gpt-6.1-sol` on Bedrock). Fields: `limits.contextWindow` and `limits.maxOutputTokens` in tokens; `capabilities` as in `ModelInfo`. A model the file does not list is unknown: the SDK uses its defaults for it, so new ids need an entry.
- `capabilities.defaultEffort`: the effort the vendor's own agent harness runs the model at by default (Claude Code, Codex, Gemini CLI), in the vendor's level names; the vendor's documented API default when it has no harness or the harness does not cover the model. Leave it out when neither is documented. Sources as of 2026-11: [Claude Code model config](https://code.claude.com/docs/en/model-config) (`high`, except `medium` for the 5.5 models and `xhigh` for Opus 4.7), Codex's bundled `codex-rs/models-manager/models.json` (`default_reasoning_level`), and Gemini CLI's `packages/core/src/config/defaultModelConfigs.ts` (`thinkingLevel: HIGH` for the Gemini 3.x models it lists). It is for the harness, which reads its own copy of this file to resolve `effort="auto"` (#4683); the SDKs skip it. Values are the harness effort levels: `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.

## `conformance.json`

Which model behaviors the SDKs check against live models, and on which models. Each SDK's integration tests read this file directly from the repository; it is not copied into a package.

- `cases`: one entry per conformance case, keyed by its id. `passes` says what the case must show. `requires` names a `ModelInfo` field (`capabilities.promptCaching`); the case applies to a model only when that field is known on the model's resolved model info, and equal to `equals` when the case gives one. A case without `requires` applies to every target. The gate reads the resolved info, not `model-info.json`, so a provider that turns a capability off is not asked to show it. `"tools": true` marks a case that needs the model to call a tool. Such a case does not apply to a target whose `model-info.json` entry says it cannot: `capabilities.toolUse` is `false`, or, on the providers that call OpenAI's Chat Completions API (`openai` and `mantle`), `capabilities.chatCompletionsTools` is `unsupported`. `ModelInfo` does not carry those two fields, so this part of the gate reads the entry.
- `targets`: the provider and model id pairs every case runs on. The ones marked `"core": true` are a small set, one or two current models per provider, chosen so that every case still runs on something; pull requests run only those. A target marked `"endOfLife": true` is a model the provider no longer serves: it stays listed as a record, no case runs on it, and results report it as `not-applicable` with the reason `end of life`. `provider` is a shared id (`anthropic`, `bedrock`, `mantle`, `mantle-responses`, `openai`, `openai-responses`, `gemini`, `mistral`) that each SDK maps to one of its model classes. To cover a new model, add its entry to `model-info.json` and a row here.
- `knownFailures`: target and case pairs that fail today for a reason we know and accept for now: a tracked bug, or a table value we set on purpose. Each entry says why in `reason`, one or two sentences, and names the `issue` in this repository that explains it. The case still runs and is recorded as `failed` with the entry's explanation, but the test run does not go red for it. An entry covers only the failure it tracks: a failed assertion, or, when the entry has `error`, an error whose message contains that text. Any other error on the pair still fails the run. The run also goes red when the case starts passing, when the case stops applying to the model, or when the entry names a target or case that is gone, so the entry is removed together with the fix. An entry marked `"intermittent": true` fails only some of the time on that target, so a pass does not turn the run red.
- `untested`: the `model-info.json` entries that no target resolves to, each with the reason, such as a model the test accounts cannot call. Every entry in `model-info.json` has a target or is listed here; a test in each SDK fails otherwise, so a model added to the table gets a decision.
- `cachePrompt`: the system prompt of the `prompt-caching` case, as an `intro` line followed by one guideline per `topics` and `actions` pair, in that order: `1. When a customer asks about <topic>, <action>.` It is long enough to pass every target's cache minimum and reads as ordinary prose, because some providers filter synthetic filler text.

Every SDK implements every case and maps every provider, or lists the ones it leaves out with a reason; a test in each SDK fails when a case id or provider id here is in neither list.

### When the cases run

The cases make live calls to every target, so they run only when `STRANDS_CONFORMANCE` is set: `core` runs the core targets and any other value, by convention `all`, runs every target. CI uses `all` for the weekly run on main, and `core` for pull requests that change the model providers, their client libraries, the shared model data or the cases themselves. To run them locally, set it yourself.

To check a single model, for example a new one, set `STRANDS_CONFORMANCE_TARGET` to `<provider>:<model id>`; the weekly workflow takes the same value as an input when started by hand. The pair does not have to be listed. Every case then runs on it, with the model info set to what the case requires, so the run shows what the model supports beyond what `model-info.json` declares. A case the model does not declare is reported, not failed, when it does not work.

### Results

When `STRANDS_CONFORMANCE_RESULTS` names a file, each run appends one JSON object per line to it, one per case and target:

```json
{"sdk": "python", "provider": "anthropic", "model": "claude-opus-5-5", "case": "prompt-caching", "status": "passed"}
```

- `sdk`: `python` or `typescript`.
- `status`: `passed`, `failed`, `error` (the provider could not serve the call: throttling, credentials, an outage, a model that is not served), `skipped` (the case applies but did not run, for example missing credentials) or `not-applicable` (the case's `requires` does not hold for the model, the model cannot call the tools the case needs, or the SDK leaves the case or provider out). Only `failed` is a verdict against the model; report `error` and `skipped` as not validated.
- `reason`: present for `error`, `skipped` and `not-applicable`.
- `known`: present when the result is the failure a `knownFailures` entry tracks. It carries the entry's `reason` and `issue`, so a report can show a known failure with its explanation, apart from a new one.
- `attempts`: present when the case took more than one attempt, so a target that often needs a retry shows up in the results.
- `declared`: present in a probe of a single model. Whether the model's own model info met the case's `requires`, so `passed` with `declared: false` is a capability that works but is not declared.

When a line repeats an earlier `sdk`, `provider`, `model` and `case`, the later line wins.
