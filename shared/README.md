# Shared

What the SDKs and the harness must agree on: data, constants and lists that exist in Python and TypeScript alike. Anything in this folder has a copy or loader in each SDK and a parity test that fails when a copy drifts.

## `model-info.json`

What the SDKs know about models: context windows, output ceilings, which models take cache points, which models Strands forces to call the structured output tool, which have native structured output, which accept temporary messages, which can defer tool schemas, which take tools on the OpenAI Chat Completions API, which need the system prompt sent as a message, which cannot call tools on their provider, and the id rules that map a provider's model id to the entry that describes it. Each entry is a `ModelInfo`, the same type the SDK exposes, plus the few fields that type does not carry (`capabilities.defaultEffort` for the harness, `capabilities.chatCompletionsTools` for the OpenAI Chat Completions provider, `capabilities.systemPromptPlacement` for the OpenAI Responses provider, and `capabilities.toolUse`, which no consumer reads yet); every field is optional and a missing field means unknown.

Edit the file; each SDK copies it into its own package when it installs and builds, and does not commit the copy:

- `strands-ts`: the `prepare` (any `npm ci` / `npm install`) and `prebuild` scripts `cp` it to `strands-ts/src/models/model-info.json` (git-ignored). Run `npm run prepare -w strands-ts` after editing to refresh it. `model-info.test.node.ts` asserts the copy equals this file.
- `strands-py`: the `hatch_build.py` build hook copies it to `strands-py/src/strands/models/model_info.json` (git-ignored). `test__model_info.py` asserts the copy equals this file.
- `harness-ts`: `prepare` / `prebuild` copy it to `harness-ts/src/model-info.json` (git-ignored); `test/model-info.test.ts` asserts the copy equals this file.
- `harness-py`: `hatch_build.py` copies it to `harness-py/src/strands_harness/model_info.json` (git-ignored); `tests/test__model_info.py` asserts the copy equals this file.

Each consumer reads only the fields it uses and skips the rest, so a field one consumer needs (the harness's `capabilities.defaultEffort`) needs no change in the others.

### Format

Keys and multi-word values are camelCase, matching the TypeScript `ModelInfo` type (`cachePoints`); the Python loader re-cases both on read (`cache_points`). There is no version field: the shape is the SDK's `ModelInfo` type, each SDK's tests validate every entry strictly against it and those few extra fields, and a shape change updates the loaders in the same PR. `capabilities.stateful` is owned by the provider and is not read from this file. `capabilities.temporaryMessages` says which models accept temporary messages and use their text; only a provider that can send them acts on it. Claude Haiku 5.5 accepts them but rarely uses the text, so it is `false`. `capabilities.forcedToolChoice` is also `false` for Claude Haiku 5.5, although the model accepts a forced tool choice: a forced call skips thinking, so its structured output uses native output instead. That makes the entry a choice, not a fact about the model; #6236 has the measurements and what would let it go back to `true`. `capabilities.deferredToolLoading` is `native` where the model vendor's own API defers tool schemas, which only a provider that sends the deferral flag acts on (for OpenAI models, the Responses API's tool search, which the SDKs' OpenAI provider uses only on `api.openai.com`, where it was measured; GPT-5.4 nano rejects it), and `unsupported` for a model that can't take a deferred tool as a stub (name and description with an open schema), such as one that constrains its tool calls to the stub's schema and sends `{}`; every other model gets stubs. Mark a model `unsupported` after a live run shows stubs fail where full specs work. A model that can't be run is marked with its family when other models in the family failed that way. `capabilities.chatCompletionsTools` records a model OpenAI's Chat Completions API limits tools for: `reasoningOff` when it accepts them only with `reasoning_effort: "none"`, `unsupported` when it accepts none. It is not part of `ModelInfo`; the SDKs' OpenAI Chat Completions provider reads it, and acts on it only for `api.openai.com` and Bedrock Mantle, where it was measured. `capabilities.systemPromptPlacement` is `message` for a model whose system prompt goes at the start of the messages rather than in the provider's system prompt field, and is left out otherwise. GPT-6.2 and later have it: they append the `instructions` field of OpenAI's Responses API after `input`, past every cache breakpoint, so it is billed uncached on every request (per OpenAI's prompt caching guide); a new entry for such a model needs it. It is not part of `ModelInfo`; only the SDKs' OpenAI Responses provider reads it, and sends the system prompt as a leading developer message. `capabilities.toolUse` is `false` for a model measured as unable to call tools on Bedrock (Converse, ConverseStream, InvokeModel), and is left out otherwise. Only `mistral.magistral-small-2509` has it: Bedrock accepts the tools but returns the model's tool call as text (`[TOOL_CALLS]echo{"value": "pineapple"}`), so no tool runs and structured output through a tool fails; [#6241](https://github.com/strands-agents/harness-sdk/issues/6241#issuecomment-6969381418) has the measurements. It is not part of `ModelInfo` and the SDKs do not act on it. TODO: measure again and remove it once Bedrock returns the call as a tool use.

- `defaults`: what the SDK assumes when a model's entry does not say, today `limits.contextWindow`. Defaults are the SDK's policy, not a fact about any model, so they live apart from `models`.
- `models`: one entry per model, keyed by the shortest id that names it (`claude-opus-5-5`, `gpt-5.4`, `amazon.nova-pro-v1:0`). A lookup tries the id as given, then without a trailing Bedrock version suffix (`-v1:0`), then without a trailing date (`-20260401`, `@20251001`, `-2026-03-05`), then with leading dot-separated segments removed one at a time. So `us.anthropic.claude-opus-5-5-20260401-v1:0`, an ARN and `claude-opus-5-5` all resolve to the one `claude-opus-5-5` entry. Add a separate entry only when the same model differs between providers (`openai.gpt-6.1-sol` on Bedrock). Fields: `limits.contextWindow` and `limits.maxOutputTokens` in tokens; `capabilities` as in `ModelInfo`. A model the file does not list is unknown: the SDK uses its defaults for it, so new ids need an entry.
- `capabilities.defaultEffort`: the effort the vendor's own agent harness runs the model at by default (Claude Code, Codex, Gemini CLI), in the vendor's level names; the vendor's documented API default when it has no harness or the harness does not cover the model. Leave it out when neither is documented. Sources as of 2026-11: [Claude Code model config](https://code.claude.com/docs/en/model-config) (`high`, except `medium` for the 5.5 models and `xhigh` for Opus 4.7), Codex's bundled `codex-rs/models-manager/models.json` (`default_reasoning_level`), and Gemini CLI's `packages/core/src/config/defaultModelConfigs.ts` (`thinkingLevel: HIGH` for the Gemini 3.x models it lists). It is for the harness, which reads its own copy of this file to resolve `effort="auto"` (#4683); the SDKs skip it. Values are the harness effort levels: `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
