# Divergences from strands-ts

User-visible differences between the Rust SDK and strands-ts at `7296caba7`. Each entry says what differs, why, and confirms that no cross-SDK wire or persisted format changes.

Rust-native differences that the design calls for (string slicing by `char`, `Result` instead of exceptions, compile-time rejection of concurrent invocation) are not listed.

| Area | Topic | Difference | Reason | Wire impact |
|---|---|---|---|---|
| Wire and types | Stream events | `ReasoningContentDelta.redacted_content` serializes as a base64 string; TS writes the `Uint8Array` as an index-keyed object (`{"0":1,...}`). Rust reads all three forms (base64, byte array, index-keyed object) | TS bug ([#6422](https://github.com/strands-agents/harness-sdk/issues/6422)): TS writes the same bytes as base64 in its later events and in messages ([RFC: redacted bytes base64](../../team/designs/0022-rust-sdk.md#decision-redacted-bytes-base64)) | Stream-event JSON only; persisted messages and snapshots are unchanged |
| Wire and types | JSON numbers | User-supplied numbers (tool input, JSON tool results, `appData`) can be written in a different form: JS writes `1e+21` and `18446744073709552000`, serde_json writes `1e21` and `1.8446744073709552e19` | serde_json formats floats with the shortest round-trip form, not the ECMAScript algorithm | None: every JSON reader parses both forms to the same value. Strands-owned fields are integers and match byte for byte. Fixture `tool_use_block_number_forms` checks value equality |
| Wire and types | JSON key order | An object with integer-like keys keeps its insertion order when Rust writes it; JS writes integer-like keys (`"1"`, `"10"`) first, in numeric order, then the others in insertion order, so `{"10","2","beta","1","alpha"}` is `1,2,10,beta,alpha` from TS | serde_json with `preserve_order` keeps the order it built or read; JS object key order is fixed by the language | JSON that TS wrote reads and writes back byte for byte, so stored sessions and snapshots round-trip unchanged. Only JSON Rust builds itself (tool input from a model, `appData` set in Rust) can order such keys differently, with equal values. Fixture `tool_use_block_integer_like_keys` checks both |
| Wire and types | JSON strings and depth | Text with a lone UTF-16 surrogate escape (`"\ud83d"`) fails to load; JSON nested deeper than 128 levels fails to load | serde_json rejects invalid Unicode escapes and caps recursion | Data only JS can produce (a lone surrogate cannot be a Rust `String`). Fixture `text_block_lone_surrogate` checks the error |
| Wire and types | Base64 | Base64 text with characters outside both the standard and URL-safe alphabets fails to load; Node's `Buffer.from` skips them. Missing padding, the URL-safe alphabet and whitespace are accepted, as in Node, and writing is standard padded base64, as in TS | Reject corrupt data rather than silently dropping characters | Only malformed input, which TS never writes |
| Wire and types | Input and structured output validation | Tool input validated against a schemars schema (`FunctionToolBuilder::input_schema_for`, `#[tool]`) and structured output are checked with JSON Schema. The error text lists the violations (`Validation failed:\n- /age: "x" is not of type "number"`); TS shows zod's issue JSON. Keys the schema does not forbid are kept in structured output, where zod strips them | zod is TS-only; Rust validates the schema it sends to the model. Callers read the output through `structured_output::<T>()`, which ignores extra keys | None: the text is model-facing feedback, not a cross-SDK format |
| Agent loop | Stream aggregation | A tool use whose input JSON does not parse does not leak into the next block: the next block of the message is what the model streamed (for example text). TS keeps the tool name, id and signature after the parse error, so the next block becomes a second tool use with the same id. The result is an error either way (`unable to parse tool input JSON`, or `MaxTokensError` whose partial message holds the following blocks) | TS bug ([#6423](https://github.com/strands-agents/harness-sdk/issues/6423)): the failed tool use's name, id and signature carry over into the next block | None: affects only the blocks yielded during, and the partial message of, a failed stream |
| Agent loop | Dropped agent stream | Dropping an `AgentStream` mid-invocation is a cancel: in-flight tool tasks are aborted, `AfterToolsEvent` does not fire for the abandoned batch, and history ending on a user turn is closed with the cancel message (`Cancelled by user` or the cancel's message), except while interrupts await a resume. An assistant tool-use message and its results enter history together, so a drop between them leaves no dangling tool use. The `MessageAddedEvent`s that had not finished (those messages and the cancel message) and a due `AfterInvocationEvent` run at the start of the next `invoke`, `stream` or `shutdown`, each from the callback the drop interrupted: callbacks that finished do not run again, the interrupted one runs again from its start. An interrupted plugin initialization likewise continues with the plugin it interrupted. TS on a consumer `break` without `cancel()` keeps running the loop to completion in `_streamCore`'s drain during tools, leaves the user turn open during model streaming, and fires `AfterToolsEvent` with `Tool execution interrupted` fallbacks | `Drop` cannot run async hooks, and history must stay re-invokable without running more model calls after the consumer left ([RFC: drop guard](../../team/designs/0022-rust-sdk.md#decision-drop-guard)) | None: history uses the TS cancel shape |
| Agent loop | `AgentResult` text log | `AgentResult`'s text skips blocks other than text, reasoning and citations with the debug log `block=<toolUseBlock> \| skipping content block type`; TS writes `Skipping content block type: toolUseBlock` through `console.debug` (`types/agent.ts:678`) | The cross-SDK structured log format (`field=<value> \| message`) through `tracing` | None: debug log text only |
| Agent loop | Agent as tool with several interrupts | A sub-agent that stops with several interrupts registers all of them on the caller with scoped ids (so `AgentResult::interrupts` lists all), but the tool's outcome carries the first, so `InterruptEvent` fires for that one; TS's `InterruptError` carries all | `ToolOutcome::Interrupt` holds one interrupt | None |
| Agent loop | Agent as tool with a session manager | `Agent::as_tool` on an agent that has a session manager and `preserve_context` other than `true` logs the conflict at error level and builds a tool whose every call returns the conflict text as an error result; TS throws from the `AgentAsTool` constructor. `Agent::try_as_tool` returns the same text as an error, as TS throws it | `as_tool` and `From<Agent> for ToolSource` are infallible conversions | None: the error text is the TS text |
| Hooks | Hook panics and errors | A panicking hook propagates to the caller of `invoke` or the stream's consumer, also on a tool call's task; only a panic inside a tool's body becomes an error result (`Error: ..` text is the panic message). A hook error on a per-tool event stops the batch (sequential: later calls do not run; concurrent: calls still running are aborted and end as `Tool execution interrupted`), `AfterToolsEvent` fires, and the invocation fails with the error | TS has no panics; a throw from a per-tool hook propagates out of the executor generator and the agent loop, as here | None |
| Tools | Tool event back-pressure | A tool's stream events wait in a bounded channel (one slot per call) until the agent stream is polled | TS pulls each tool generator, so a tool never runs ahead of a slow consumer | None |
| Tools | Concurrent tool interrupts | When several tools of one concurrent batch interrupt, an `InterruptEvent` fires for every interrupt; TS rethrows only the last tool's `InterruptError`, so it fires events for that tool's interrupts only. `AgentResult::interrupts` is the same in both (every unanswered interrupt) | All interrupts are registered either way; reporting every one is consistent with the result | None |
| Tools | `#[tool]` input schemas | An `Option<T>` parameter is optional and nullable (`{"type": ["string", "null"]}`), where zod's `.optional()` writes `{"type": "string"}`; `null` and a missing key both mean `None`. Struct-typed parameters get `additionalProperties: false` only when the struct declares `deny_unknown_fields`, where every zod object has it; the root input object always has it. Property keys follow schemars' order (`type` before `description`) | The schema is what schemars derives from the Rust types, normalized as `tools::schema_for` does | None: tool specs are model-facing, not a cross-SDK wire or persisted format |
| Tools | `#[tool]` descriptions and errors | A `#[tool]` without a doc comment or `description = ".."` (or with an empty override) does not compile; TS `tool()` defaults the description to `""` and the registry rejects the tool when the agent is built. Registry validation errors name the tool: `tool_name=<name> \| Tool description must be a non-empty string` (the TS text, which TS tests match as a substring, after the prefix). A `#[tool]` body may return any `E: Into<BoxError>` (`String`, `&str`, `BoxError`), each an error result with `Error: <message>` | Fail at compile time what fails at construction anyway; name the tool in an error that otherwise does not say which | None: compile-time checks and error text |
| Models | Lone surrogates in requests | No repair pass before a model call or token count: a Rust `String` is always valid UTF-8, so a request cannot hold a lone UTF-16 surrogate. Text with a lone surrogate escape fails to load (see JSON strings and depth), and length-based cuts fall on character boundaries. strands-ts sends lone surrogates in messages, the system prompt and tool specs as U+FFFD and warns once | `String` cannot represent a lone surrogate | None: nothing is persisted or sent differently |
| Models | Retry strategy names | The duplicate-strategy warning and the attach error name the strategy by `name()` (`strands:default-model-retry-strategy`); TS uses the class name | No constructor name without `Any` | None |
| Models | Bedrock error mapping | A `ThrottlingException` that rejects the request itself (HTTP 429, after the AWS SDK's own retries) is a `ModelThrottledError`, and a connection failure or timeout is a `ModelNetworkError`, so the default model retry strategy retries both. strands-ts maps only the in-stream `throttlingException` and rethrows the others unchanged (they become a plain `ModelError`) | TS bug ([#6424](https://github.com/strands-agents/harness-sdk/issues/6424)): a throttle that rejects the request is never retried. The Anthropic and OpenAI providers classify throttles and transport failures the same way ([RFC: own HTTP providers](../../team/designs/0022-rust-sdk.md#decision-own-http-providers)), and the Python SDK maps both throttle paths | None |
| Models | Bedrock user agent | Requests carry the SDK app name `strands-agents-rust-sdk` (`app/strands-agents-rust-sdk` in the user agent) unless `sdk_config` sets one; TS sets `customUserAgent: 'strands-agents-ts-sdk'` and appends it to a caller's agent | The Rust AWS SDK has an app name, not a free-form user agent string | None |
| Models | Bedrock cache warning field | The warning that a Nova model takes no tool-level cache point names the setting `tools_ttl=<..>`; TS writes `toolsTTL=<..>` | The Rust option is `CacheConfig::tools_ttl` | None: log text only |
| Models | Bedrock response JSON | Converse (non-streaming) tool inputs and `additionalModelResponseFields` arrive through the AWS SDK's unordered document type, so their key order can differ from the service's; guardrail trace automated-reasoning findings keep only their kind (`{"valid": {}}`). Streamed tool input is a string and keeps its order | The Rust SDK models documents as hash maps and the findings as deep nested unions | Values are equal; only key order and the finding details differ |
